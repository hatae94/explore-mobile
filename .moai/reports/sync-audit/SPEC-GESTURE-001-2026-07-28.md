### F1 — `scroll` sends a zero-distance swipe and reports success
**[HIGH][certain]** `src/cli/commands/scroll-geometry.ts:112-136` (`computeScrollSwipe`), surfaced via `src/cli/commands/scroll.ts:104-114`

`Math.round` collapses `from` and `to` to the same pixel for small ratios. On the real 402×874
screen, every `--amount ≤ 0.0012` yields `from.y === to.y === 437`; the horizontal axis is worse
(`--amount 0.002` still yields `from.x === to.x === 201`).

Live reproduction:
```
$ node dist/cli/bin.js scroll down --amount 0.001 --device D0B3A18C-…
{"ok":true,"command":"scroll","data":{"direction":"down","from":{"x":201,"y":437},"to":{"x":201,"y":437}}}
scrollY: 3212 -> 3212        # exact oracle, no movement
screenshot SHA-256: 17f76bf957993c35… -> 17f76bf957993c35…   # byte-identical
```
This is the failure class the SPEC was revised twice to prevent, and it also falsifies
AC-GEST-007 and AC-GEST-016 (`to.y < from.y` does not hold).

**Required fix**: after rounding, assert the gesture is non-degenerate. In `computeScrollSwipe`,
if `from` equals `to` on the scroll axis, either widen to a minimum travel of ≥1px, or return a
signal that `scrollCommand` converts into a new rejection (e.g. `AMOUNT_TOO_SMALL`) that sends
zero gestures. Add a unit test asserting `from !== to` for every direction across
`--amount ∈ {0.0001, 0.001, 0.0012, 1}`.

### F2 — `swipe` without `--duration` is a silent no-op on iOS, reported as `ok:true`
**[HIGH][certain]** `src/cli/commands/swipe.ts:77-90` + `src/backend/idb-backend.ts:317-324`; documented at `README.md:234-235`

`--duration` is optional and README says "omit it to use the platform default duration". On the
only platform this SPEC actually verified, the platform default produces no movement at all.

Live reproduction (exact `window.scrollY` oracle, with ~2370px of scroll headroom available):
```
$ node dist/cli/bin.js swipe 201 634 201 240 --device D0B3A18C-…
{"ok":true,…}                 scrollY: 1930 -> 1930      # run 1
{"ok":true,…}                 scrollY:  843 ->  843      # run 2
$ node dist/cli/bin.js swipe 201 634 201 240 --duration 500 --device D0B3A18C-…
{"ok":true,…}                 scrollY:  843 -> 1485      # control, works
```
The project already knows this: it is the documented justification for
`SCROLL_SWIPE_DURATION_MS` (`src/cli/commands/scroll.ts:33-46`) and is stated plainly at
`README.md:295-300`. The workaround was applied *inside* `scroll` only; `swipe` still exposes the
broken mode as its primary documented form. AC-GEST-005 was verified with `--duration 500` only,
so no AC covers this branch — it is a hole in the AC set rather than an AC violation.

**Required fix**: pick one and make the docs match. Either (a) give `swipe` the same non-zero
default duration `scroll` uses when `--duration` is omitted, or (b) keep pass-through and change
`README.md:234-235` to state that omitting `--duration` is measured to be a no-op on the iOS
simulator and that a value should always be supplied. (a) is preferable — it removes the trap
rather than documenting it. Add an AC/test covering the omitted-duration branch end-to-end.

### F3 — `--duration 0` is accepted and is a silent no-op, reported as `ok:true`
**[MEDIUM][high]** `src/cli/validators.ts:41-43` (`parseDurationMs` accepts `0`); README documents "non-negative integer"

```
$ node dist/cli/bin.js swipe 201 634 201 240 --duration 0 --device D0B3A18C-…
{"ok":true,…,"durationMs":0}     scrollY: 843 -> 843       # no movement
```
`0` reaches `idb` as `--duration 0` and `adb` as a trailing `0`. Same class as F2, but this one is
an explicitly-documented-valid input.

**Required fix**: reject `0` at the validator with `INVALID_DURATION` (make the rule *positive*
integer), or clamp to a floor. Update the README's "non-negative integer" wording accordingly, and
mirror the change into AC-GEST-002.

### F4 — `js-click-scrolled` claims a scroll that did not happen
**[MEDIUM][certain]** `src/cli/commands/web-support.ts:257-271`; docs at `README.md:413-418` and the CHANGELOG `method` bullet

`activateElement` sets the `-scrolled` suffix from `scrolled === true`, but
`buildScrollIntoViewExpression` returns `true` merely because the node **exists** — it says nothing
about whether the page moved.

Proven live on the current page (Wikipedia's off-canvas drawer links — 275×45, non-zero size so
they survive the normalizer's visibility filter, centre off-viewport so the coordinate is
unconvertible):
```
idx 1 "Home"   preRect {x:-275,y:-1,w:275,h:45}  scrollIntoView->true
   scrollY 1485 -> 1485   pageActuallyMoved:false   postRect identical
   METHOD THE CLI WOULD REPORT: "js-click-scrolled"
```
The repo's own AC-WEB-013 fixture encodes the same overstatement: its harness comment says the
default is *"i.e. scrolling changed nothing"*, and it asserts `js-click-scrolled`.

This makes two published statements false: `README.md:415-418` ("the caller needs to know the page
moved") and the CHANGELOG's "whether the page's scroll position changed as a side effect, which it
never does silently". `native-scrolled` is **not** affected — a successful re-measure implies real
movement.

**Required fix**: make the suffix mean what it claims. Read `window.scrollX/scrollY` inside
`buildScrollIntoViewExpression` before and after the call and return whether it changed; set
`-scrolled` only on a real delta. Cheaper alternative: leave the behavior and correct the README
table + CHANGELOG to say "scrollIntoView was attempted", not "the page moved".

### F7 — `--duration` has no upper bound; extreme values produce malformed argv
**[LOW][high]** `src/cli/validators.ts:41-43`

`parseDurationMs` accepts any `^\d+$`. Consequences computed from the exact
`String(durationMs / 1000)` / `String(durationMs)` expressions:

| input | `idb` argv | `adb` argv |
|---|---|---|
| `1000000000000000000000000` | `1e+21` | `1e+24` — not an integer; `adb` would reject |
| `9007199254740993` | `9007199254740.992` | `9007199254740992` — ≠ input (float precision) |
| `600000` | `600` | `600000` — a 10-minute blocking swipe |

Not a security boundary (the caller already controls argv), but a robustness gap.

**Required fix**: cap `--duration` at a sane ceiling (e.g. 60000 ms) and reject above it with
`INVALID_DURATION`.

### F8 — Zero `@MX:` tags across the three new files
**[LOW][certain]** `src/cli/commands/{swipe,scroll,scroll-geometry}.ts`

### F10 — Witness rule accepts an origin-anchored element that overspans the screen
**[LOW][medium]** `src/cli/commands/scroll-geometry.ts:52-73`

The witness is validated against the candidate the same element produced, so a single top-level
element at the origin is always its own witness:
```
[{0,0,402,3000}, {0,0,402,874}, {0,800,402,74}]  ->  {width:402, height:3000}
```
`scroll down --amount 1` would then swipe to `y≈2850` on an 874-tall screen. The rule as designed
rejects the *fragments* case (AC-GEST-017, verified) but not the *overspan* case.

I could **not** reproduce this on real hardware — the live iOS dump yields exactly two top-level
elements with `Application` at `{0,0,402,874}`, and `deriveScreenSize` iterates top-level entries
only (`CommonElement` is a tree with `children`), so nested oversized frames cannot leak in.
Android `uiautomator` bounds are screen-clipped. Hence medium confidence and low severity: a real
trigger requires a top-level element larger than the screen, which neither backend produced here.

**Required fix**: optional. If cheap, reject a candidate whose dimensions exceed the largest
plausible device bounds, or require the witness to be a *different* element from the sole extent
contributor.

## Things I checked that turned out to be non-issues

Recording these so they are not re-litigated:

1. **`SCROLL_SWIPE_DURATION_MS` discoverability** — the user's specific concern. It **is** guarded.
   `scroll.test.ts:113` asserts `expect(call[3]?.durationMs).toBeGreaterThan(0)`. I mutation-tested
   it: replacing the options object with `undefined` makes the suite fail (1 failed / 20 passed).
   A future change cannot silently regress scrolling to a no-op. Hardcoding is defensible here.
2. **"top-level element" wording in README/CHANGELOG/code comments** — accurate. `CommonElement`
   carries `children: CommonElement[]`, and `deriveScreenSize` iterates only the top-level array.
   Docs and code agree.
3. **Sub-pixel bounds** (`h: 14.333333333333371`, present in the live dump) — fails *safe*. Float
   inequality can only cause a missed witness → `SCREEN_SIZE_UNKNOWN` → zero gestures, never a
   wrong accepted size. Live dump derived `402x874` correctly despite a sub-pixel element.
4. **`AC-WEB-013` expectation change (`js-click` → `js-click-scrolled`)** — a legitimate
   consequence, **not** a masked regression. The load-bearing assertion `expect(h.taps).toEqual([])`
   is unchanged, and M4 *added* a guard test ("does not credit a scroll that never happened when
   scrollIntoView finds no node", `scrollResult: false` → `js-click`). Only the label moved. The
   separate problem is that the label itself overstates (F4).
5. **Zero-size elements as a `js-click-scrolled` vector** — not reachable.
   `webdom.ts:175` drops `w <= 0 || h <= 0` before selection.
6. **Rejection paths sending gestures** — none do. 15 variants run through the real CLI with the
   screenshot hash byte-identical before and after (`cb13a9491007fb68` → `cb13a9491007fb68`).
7. **Shell injection** — none. `spawn` + argv arrays throughout; no `shell: true`, no
   `child_process.exec` (all `exec(` hits are the project's own injectable `ProcessExecutor`).
8. **Android honesty** — three prominent disclosures (README header 20-21, Status 613-615, roadmap
   651) plus the CHANGELOG all state "argv-verified only". The PARTIAL is honest. The only gap is
   locality (F6).
9. **Stale numbers** — none. 510 tests, 17 ACs, 16/1/0, "existing 8 methods" → 9 all check out.
   CHANGELOG's "438 total" sits in the SPEC-WEBVIEW-001 entry and is historically correct.
10. **Tier M classification** — defensible. ~584 production LOC across 12 production files, inside
    the 300–1000 LOC / 5–15 file envelope (the 2799-insertion diff stat is mostly tests and docs).
