## 1. SPEC이 "확인 불가"로 적었던 항목들이 확인됐다

### §C.2 — "adb가 이 머신에 설치돼 있지 않다"는 부정확했다

SPEC은 `command -v adb` → `command not found` 하나를 근거로 **미설치**로 기록했다. 실제로는 **설치돼 있고 PATH에만 없었다**:

```
/Users/hatae/Library/Android/sdk/platform-tools/adb
```

`command -v`는 "PATH에서 실행 가능한가"를 묻지 "설치돼 있는가"를 묻지 않는다. 단일 명령의 실패를 더 강한 명제로 일반화한 것이 오류의 형태다.

### §C.1-⑥ — `adb shell input swipe` 문법 (그동안 **미실측**, "로컬 수단으로 승격 불가")

**확인됨.** 원시 adb와 CLI 경로 양쪽에서 실기기 화면이 실제로 움직였다.

```
$ adb -s <serial> shell input swipe 1100 1560 340 1560 500   → exit 0, 화면 전환 확인
$ node dist/cli/bin.js swipe ... --duration 500 --device <serial>
  {"ok":true,...,"durationMs":500}                            → 화면 전환 확인
```

ms 단위 지속시간 인자도 그대로 통했다. SPEC §F의 Android 열(`input swipe x1 y1 x2 y2 [ms]`)이 맞다.

### §C.1-④ — Android 루트 노드 bounds = 화면 전체 (그동안 **픽스처 근거뿐**)

**실기기 확인.** 홈 화면과 설정 화면 양쪽에서:

```
최상위 요소 1개: {x:0, y:0, w:1440, h:3120}  android.widget.FrameLayout
후보 크기 1440×3120 · witness 존재 ✓
```

witness 규칙(REQ-GEST-SCROLL-002)이 Android 실기기에서 성립한다. 다만 이 기기는 **단일 루트**였고, 정규화기가 다중 최상위를 낼 수 있다는 §C.1-⑨은 여전히 픽스처 근거다.

### 기기 인식

`isEmulator: false`, `platform: android`, `osVersion: 16`, `connectionState: device` — 물리 기기가 정확히 분류됐다. 무선 ADB의 긴 시리얼(`...._adb-tls-connect._tcp`)도 `-s`로 문제없이 전달된다.

### 동작 확인된 명령

`devices` · `screenshot` · `dump` · `launch` · `swipe` · `scroll`. `scroll down`/`up`의 방향 의미도 정확했다(`to.y < from.y` for down, 화면 실제 이동).

**단, iOS와 다른 점:** `scroll down` → `scroll up` 왕복이 원위치로 정확히 돌아오지 않았다. Android의 관성 스크롤(fling)로 보이며, iOS 시뮬레이터에서는 정확히 대칭 복귀했다.

## 2. [중요] SPEC의 근거가 사실과 다르다 — 문턱 미만 스와이프는 무동작이 아니라 **탭**이다

REQ-GEST-SCROLL-007은 1px 클램프를 거부하며 이렇게 적었다:

> 1px은 어떤 터치 슬롭 임계값보다도 작아 기기에서는 여전히 **아무 일도 일어나지 않을 가능성이 크다**

**사실이 아니다.** 터치 슬롭보다 짧은 드래그를 Android는 **탭으로 해석한다.** 시작점 아래에 있는 요소를 활성화한다.

실증(의도치 않게):

```
화면중앙 (720, 1560)에서 11~80px 짧은 스와이프 반복
  → 그 좌표의 요소:  y 1496~1566  "페어링 코드로 기기 페어링"
  → 결과: 페어링 바텀시트가 열림
```

### 함의

1. **가드는 더 필요해졌다.** `AMOUNT_TOO_SMALL`의 정당화가 "헛수고 방지"에서 **"의도치 않은 탭 방지"** 로 강해진다. 무효과가 아니라 오작동이다.
2. **11pt 측정의 판정 기준이 안전하지 않다.** M7은 "화면이 안 움직임 = 아무 일도 없었음"으로 판정했다. 실제로는 "탭이 발생했을" 수 있다. iOS 측정이 이를 못 본 이유는 **상호작용 요소가 없는 체커보드 페이지**에서 쟀기 때문이다 — 방법론이 우연히 이 현상을 가렸다.
3. **§C.3의 알려진 한계 서술이 불완전하다.** "스와이프는 보냈지만 화면이 움직였는지 모른다"에 더해 "움직이지 않았다면 대신 탭이 됐을 수 있다"가 필요하다.

`tappable=false`인 요소였는데도 탭이 먹었다는 점도 기록해 둔다(정규화기의 `tappable` 파생과 실제 클릭 처리기가 다른 계층에 있음을 시사).

## 3. `launch`가 기존 태스크를 되살린다

`AdbBackend.launchApp`은 런처 인텐트를 쓴다:

```
am start -a android.intent.action.MAIN -c android.intent.category.LAUNCHER ...
```

Android는 이 인텐트로 앱의 **기존 태스크를 재개**한다. 앱 최상위 화면이 아니라 마지막으로 보던 하위 화면으로 돌아간다.

관측: 사용자가 무선 ADB를 설정하며 설정 앱이 "무선 디버깅" 화면에 있었고(`t15468`), `launch com.android.settings`를 부를 때마다 그 화면으로 복귀했다.

자동화 관점에서 중요하다 — `launch`가 **결정적인 시작 상태를 보장하지 않는다.** SPEC-ANDROID-001 영역이며 문서화 가치가 있다.

## 4. Android 터치 슬롭 문턱 — **측정 완료: 8dp**

### 4.0 1차 시도는 폐기됐다

첫 시도의 수치(11px 1/5, 24·40·80px 0/5)는 **무효**다. 측정 화면("기기 페어링")이 스크롤되지 않았고, 짧은 스와이프가 탭으로 해석돼 "이동"으로 잡힌 변화가 실은 바텀시트 열림이었다.

### 4.1 2차 측정 조건 (1차 실패를 교정)

- **전용 페이지**: 로컬 체커보드 20000×3000px, **상호작용 요소 0개**(`<a>`/`<button>`/`onclick` 없음). `adb reverse tcp:8935`로 기기 localhost에 매핑, Chrome으로 진입.
- **오라클**: 상태바(상단 250px) 제외 본문 스크린샷 해시. **잡음 기준선 선행 확인 — 무제스처 4회 전부 동일**(설정 화면에서는 3회가 전부 달라 부적합했다).
- **좌표 사전 확인**: (720,1560) 아래에 레이아웃 컨테이너와 WebView뿐, `tappable` 요소 0개.
- 스크롤 여유 사전 확인 + 이동 감지 시 즉시 역방향 복원.
- **정확한 거리**: 시작 y=1560 고정, 끝 y=1560−d. (1차 정밀화에서 `half=d/2` 정수 나눗셈이 홀수 거리를 1px 깎던 것을 제거.)

### 4.2 결과 — 세로축

| 거리 | 이동 |
|---|---|
| 5 / 11 / 20 / 28 / 29 / **30** px | **0/5 ~ 0/8** |
| 31 px | 6/8 (확률적 전환) |
| **32 px** | **8/8** |
| 35 / 40 / 45 / 50 px | 5/5 |

### 4.3 결과 — 가로축 (등방적)

| 거리 | 이동 |
|---|---|
| 11 px | 0/6 |
| **30 px** | **0/6** |
| 31 px | 5/6 |
| 32 px | 5/6 |

### 4.4 정체 — 이것은 기기 상수가 아니라 **플랫폼 규칙**이다

```
wm density → Physical density: 600   (600/160 = 3.75x)
Android 표준 터치 슬롭 = 8dp
8dp × 3.75 = 30.0 px
```

측정된 경계와 **정확히 일치한다.** 30px에서 실패하고 31px부터 움직이므로, 규칙은 `distance > touchSlop`(같으면 안 되고 **초과**해야 함)이다. 이는 `ViewConfiguration.getScaledTouchSlop()`의 동작과 부합한다.

**따라서 Android 문턱은 픽셀 상수가 아니라 `8dp × density`로 파생돼야 한다.** 밀도가 다른 기기에서 자동으로 맞는다:

| 밀도 | 배율 | 슬롭 |
|---|---|---|
| 420dpi | 2.625x | 21px |
| 480dpi | 3.0x | 24px |
| 600dpi | 3.75x | **30px** (본 측정) |
| 640dpi | 4.0x | 32px |

`wm density`로 런타임 조회가 가능하다.

### 4.5 [중대] iOS 값 11pt는 Android에서 전혀 통하지 않는다

이 기기에서 **11px는 세로 0/5, 가로 0/6** — 한 번도 안 움직였다. 슬롭(30px)의 약 1/3이다.

즉 현재 CLI가 Android에서 반환하는 `AMOUNT_TOO_SMALL`의 `minValidRatio`는 **아무 일도 하지 않는 값을 권고한다.** sync-auditor가 2차 감사에서 N3로 지적했던 결함("오류 코드의 행동 가능 정보가 호출자를 같은 결함으로 되돌려보낸다")이 **Android에서 그대로 재현된다.** SPEC이 "iOS 값은 Android의 근거가 아니다"라고 명시한 것은 옳았고, 이제 그것이 실측으로 확인됐다.

### 4.6 권고 문턱

- 세로 32px는 8/8, 가로 32px는 5/6이었다. 슬롭+1(31px)은 양축 모두 확률적이다.
- 보수적으로 **`floor(8dp × density) + 2px`** 이상을 권고한다(본 기기 32px). 신뢰 100%를 원하면 여유를 더 둔다.
- 이 값은 **1대(SM-S938N, Android 16, 600dpi)** 에서 측정됐다. 다른 제조사·OS 버전은 미확인이나, 8dp는 AOSP 기본값이라 파생 규칙 자체는 이식성이 높다.

## 부수 관측

- `AMBIGUOUS_DEVICE`가 또 걸렸다 — 꺼진 iOS 시뮬레이터 22대를 세어 "24 devices". sync-auditor가 INFO → LOW-MEDIUM으로 올린 그 결함이며, Android 기기가 붙으니 **모든 명령에 `--device`가 강제된다.** 실사용 마찰이 확인됐다.
