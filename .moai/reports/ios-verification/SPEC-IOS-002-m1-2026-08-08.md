## 0. 착수 시점 상태 — 왜 아이패드인가

이 세션은 아이폰으로 시작하려다 사용자 지시로 아이패드로 바꿨다. 그 판단을 뒷받침하는 관측이 나왔다.

```
$ idevice_id -l
00008103-000458360A63401E
```

**아이패드 하나만 나온다.** 아이폰(`00008130-001238880C13803A`)은 `idevice_id`(usbmuxd 경유) 목록에 없다.

반면 `devicectl`은 둘 다 본다:

```
$ xcrun devicectl list devices
Name          Hostname                               Identifier                             State                Model
하태용의 iPad     hataeyong-ui-iPad.coredevice.local     D2C63314-8AA3-5C85-8EFC-0A4B600CB1A1   available (paired)   iPad Pro (12.9-inch) (5th generation) (iPad13,8)
하태용의 iPhone   hataeyong-ui-iPhone.coredevice.local   DEDABBFA-9696-54A0-A2EE-A6812D9FDFEB   available (paired)   iPhone 15 Pro Max (iPhone16,2)
```

**여기서 읽히는 것**

- `devicectl`의 `State: available (paired)`는 **USB 연결을 뜻하지 않는다.** 두 기기 모두 `available (paired)`이지만 usbmuxd 경유로 잡히는 것은 아이패드뿐이다. 네트워크 페어링만으로도 `available (paired)`가 된다.
- 따라서 **`devicectl`의 `State`를 "iproxy를 쓸 수 있는가"의 신호로 삼으면 안 된다.** 아이폰은 `available (paired)`이면서 `iproxy -u`가 붙을 USB 전송이 없다.
- `iproxy`가 쓸 UDID의 권위 있는 출처는 `idevice_id -l`이다.
- **식별자 두 종류가 다르다는 것이 여기서도 확인된다**: `devicectl`의 `Identifier`(`D2C63314-8AA3-5C85-8EFC-0A4B600CB1A1`)와 `iproxy`가 쓰는 UDID(`00008103-000458360A63401E`)는 서로 다른 값이다.

## 2. 관문을 되돌리기 전의 출발 상태

### 2.1 CLI가 보는 상태 (터널 없음)

```
$ node dist/cli/bin.js devices
... iPad  : connectionState=unavailable, unavailableReason="disconnected — 터널이 연결되지 않았다 — WDA·신뢰 설정을 확인한다"
... iPhone: connectionState=unavailable, unavailableReason="disconnected — 터널이 연결되지 않았다 — WDA·신뢰 설정을 확인한다"
```

### 2.2 `doctor`가 iOS 진단을 내지 못한다 — 새로 발견

```
$ node dist/cli/bin.js doctor --device 00008103-000458360A63401E
{"ok":true,"command":"doctor","data":{"adb":{...},"daemon":{"healthy":true},"devices":[...],
 "adbKeyboard":{"skipped":true,
  "reason":"Cannot install/enable ADBKeyBoard: Device '00008103-000458360A63401E' exists but is not connected (connectionState: 'unavailable'). Reconnect or boot it, then retry."}}}
```

**`wdaEnvironment` 키가 출력에 없다.**

경로를 코드에서 확인했다 — `src/cli/commands/doctor.ts`:

- 59행 `resolveTargetDevice(devices, args.device, source)`가 `unavailable` 기기에 대해 실패를 반환한다.
- 60행 `resolvedDevice`가 `undefined`가 된다.
- 62행 `if (resolvedDevice?.platform === "ios")` 조건이 성립하지 않아 **iOS 갈래로 들어가지 못한다.**
- 101행 `if (!target.ok)` 분기로 떨어지고, 106행이 위 `reason` 문구를 만든다. 출력의 문구가 이 줄의 것과 일치한다.

**여기서 읽히는 것**

- **iOS 진단이 가장 필요한 상태(기기가 안 올라온 상태)에서 iOS 진단이 나오지 않는다.**
- 이것은 `acceptance.md` AC-IOS2-018이 요구하는 *"iOS 준비가 미완인 상태에서 진단을 실행하면 관문 3개가 각각 별개 필드로 보고된다"*를 **현재 구조로는 도달 불가**로 만든다. M6에서 관문 감지를 구현해도, 그 결과를 실어 나를 `wdaEnvironment` 자체가 이 상태에서는 생성되지 않는다.
- 이 파일 상단의 `@MX:WARN`(`wda-doctor.ts` 10-16행)이 막는 회귀 — *"WDA 미기동이면 iOS 기기가 목록에서 통째로 사라진다"* — 와 **같은 계열의 다른 표면**이다. 기기 목록(`devices`)에서는 살아남았지만, 진단 보고(`doctor`)에서는 사라진다.
- 이 발견은 M2·M6의 범위 판단에 영향을 준다. 관측 사실로만 여기 남기고, 처리 방침은 SPEC 문서 담당이 정한다.

```
00008103-000 unavailable disconnected — 터널이 연결되지 않았다 — WDA·신뢰 설정을 확인한다
00008130-001 unavailable disconnected — 터널이 연결되지 않았다 — WDA·신뢰 설정을 확인한다
```

**여기서 읽히는 것 — 이 절이 이 기록에서 가장 값진 관측이다**

- **로컬 터널(`iproxy`)이 8100에서 LISTEN 중인데도 `unavailableReason`은 "터널이 연결되지 않았다"로 그대로다.** 문구가 로컬 터널 상태를 반영하지 않는다.
- 즉 이 문구의 "터널"은 `iproxy`가 만든 로컬 포워딩이 아니라 **다른 것**(`devicectl`이 보고하는 값)을 가리킨다. 사용자가 이 문구를 읽고 `iproxy`를 띄우면, 띄운 뒤에도 같은 문구를 보게 된다 — **복구 절차를 밟았는데 메시지가 변하지 않는 상태**다.
- 이 문구는 **관문 감지 신호 후보에서 이미 제외돼 있다**(`research.md` §2.3 · `progress.md` §E.1.1 — 시점 종속성 때문). 이번 관측은 그 제외 결정을 **다른 이유로도** 뒷받침한다: 시점 종속일 뿐 아니라 **로컬 상태와도 무관**하다.
- `http_code=000`(연결 실패)과 `iproxy`의 LISTEN이 공존한다 — `iproxy`는 로컬 소켓을 열지만 기기 쪽 8100에 수신자가 없으면 연결이 즉시 끊긴다. **`iproxy` 프로세스 생존은 WDA 도달성의 신호가 아니다.**

## 3.4 관문 감지 신호 — **관문 1개 확정** (research.md §2 산출물)

### 신호: UI 자동화 승인 미충족

| 항목 | 값 |
|---|---|
| 관문 | UI 자동화 승인 (사람 관문 3개 중 1개) |
| 관측 명령 | `xcodebuild test-without-building -xctestrun <path> -destination "id=<UDID>"` |
| 종료 코드 | `65` |
| 판별 문구 | `Timed out while enabling automation mode.` |
| 동반 문구 | `Failed to initialize for UI testing` / `The test runner failed to initialize for UI testing.` |
| 오류 도메인 | `com.apple.dt.XCTest.XCTFuture` **Code=1000** |
| `/status` 동반 상태 | `http_code=000` (연결 실패 — 러너가 뜨지 못했으므로) |
| 소요 | 약 64초 (타임아웃 대기) |

### `design.md` §I.3 우선순위에 따른 판정 — 어느 재료를 쓸 것인가

`design.md` §I.3은 **종료 코드 → 구조화된 필드 → 자유 문구** 순으로 고르라고 정한다. 이 관측에 적용하면:

| 순위 | 후보 | 이 관측에서 |
|---|---|---|
| 1 | 종료 코드 | **쓸 수 없다.** `65`는 `xcodebuild`의 일반 테스트 실패 코드이며 이 관문에 고유하지 않다. 다른 원인의 실패도 65를 낸다 |
| 2 | 구조화된 필드 | **부분적으로 가능.** `Error Domain=com.apple.dt.XCTest.XCTFuture Code=1000`은 문구보다 구조적이다. 다만 `Code=1000`이 이 관문에만 대응하는지는 **미확인** — 다른 XCTFuture 실패도 1000을 쓸 수 있다 |
| 3 | 자유 문구 | `Timed out while enabling automation mode.` — 가장 특정적이지만 **도구 버전 종속** |

**결론(잠정)**: 2순위(`XCTFuture Code=1000`)와 3순위(문구) 중 어느 것도 단독으로 확정할 수 없다. `Code=1000`의 배타성이 미확인이기 때문이다.

**따라서 지금 확정하지 않는다.** `design.md` §E.2가 정한 대로, 모르는 상태에서 규칙을 쓰면 그것은 설계가 아니라 추측이다.

### 이 신호를 채택할 때 반드시 함께 적어야 하는 것

`acceptance.md` AC-IOS2-021과 `design.md` §I.3이 정한 의무 — **3순위(자유 문구)를 채택하면 그 종속성을 코드 주석과 `SKILL.md` 양쪽에 명시한다.** 이 저장소에는 문구를 정책으로 취급했다가 반증된 이력이 있다.

적어야 할 문장의 취지: *"이 판정은 `xcodebuild` / XCTest의 출력 문구에 종속되며, Xcode 버전이 바뀌면 낡는다."*

### 아직 모르는 것 (M6 진입 전에 닫히지 않아도 되는 것 / 닫혀야 하는 것)

| 미확인 | 닫아야 M6 가능한가 |
|---|---|
| `XCTFuture Code=1000`이 이 관문에 배타적인가 | **아니오** — 배타성이 없으면 3순위 문구로 내려가면 된다 |
| 나머지 관문 2개(개발자 모드 · 인증서 신뢰)의 신호 | **각각 별개** — 하나를 못 찾아도 그 관문만 "구분 불가"로 보고한다 (AC-IOS2-019) |

## 3.5 정상 상태의 기준값 — REQ-004 판정 근거 실측

`design.md` §A가 판정 후보 3개를 갈랐던 그 호출들을, **정상 상태에서** 다시 재어 기준값으로 남긴다.

```
$ for i in 1 2 3; do curl -s -o /tmp/shot.json \
    -w "time_total=%{time_total}s size=%{size_download} code=%{http_code}\n" \
    http://127.0.0.1:8100/screenshot; done
회차1  time_total=0.679954s  size=10711240 bytes  code=200
회차2  time_total=0.678159s  size=10711240 bytes  code=200
회차3  time_total=0.670464s  size=10711240 bytes  code=200

$ for i in 1 2 3; do curl -s -o /dev/null \
    -w "time_total=%{time_total}s size=%{size_download} code=%{http_code}\n" \
    http://127.0.0.1:8100/status; done
회차1  time_total=0.006160s  size=522 bytes  code=200
회차2  time_total=0.005806s  size=522 bytes  code=200
회차3  time_total=0.005626s  size=522 bytes  code=200

$ curl -s http://127.0.0.1:8100/wda/locked
{ "value" : false, "sessionId" : null }        # http_code=200
```

| 호출 | 정상 상태 응답 | 시간 | 크기 |
|---|---|---|---|
| `GET /status` | 200 | **6 ms** | 522 B |
| `GET /screenshot` | 200 | **680 ms** | **10,711,240 B (10.2 MiB)** |
| `GET /wda/locked` | 200 (`false`) | — | — |

### 3.5.1 `design.md` §A.4의 수치가 반증됐다

`design.md` §A.4는 이렇게 적는다:

> `/screenshot`은 이미지를 전송한다(**기록상 111ms, 약 1MB 규모**). 판정 한 번에 그 비용을 낸다. **수용한다.**

실측은 다르다.

| 항목 | §A.4 기재 | 이번 실측 (iPad Pro 12.9") | 배수 |
|---|---|---|---|
| 시간 | 111 ms | **680 ms** | 약 6배 |
| 크기 | 약 1 MB | **10.2 MiB** | 약 10배 |

**원인 추정(추론이며 관측이 아니다)**: 기존 수치는 아이폰에서 잰 것으로 보인다. iPad Pro 12.9"는 화면이 훨씬 크므로 PNG가 그만큼 커진다. 즉 이 수치는 **낡은 것이 아니라 기기 종속**이다 — 어느 기기에서 쟀는지를 적지 않으면 어느 값도 정확하지 않다.

**영향**: §A.4의 "수용한다"는 결론은 111ms/1MB를 전제로 내려졌다. 680ms/10.2MiB에서도 `doctor` 한 번에 0.7초라면 여전히 수용 가능해 보이나, **그 판단은 §A.4가 내린 것이 아니다** — 전제가 달라졌으므로 결정을 다시 확인해야 한다.

**이 파일은 이 값을 기록만 한다.** `design.md` 본문 수정은 SPEC 문서 담당의 몫이다.

### 3.5.2 `doctor`의 현재 보고 — 교체 전 기준선

```
$ node dist/cli/bin.js doctor --device 00008103-000458360A63401E
"wdaEnvironment": {
    "devicectl": { "available": true },
    "wda": {
        "reachable": true,
        "port": 8100,
        "portMapDeclared": false,
        "build": "WDA 16.1.1 / iOS 26.5.2 / ipad"
    }
}
```

**여기서 읽히는 것**

- `wda`에 **조작 가능성을 담는 필드가 없다.** `reachable`(=`/status` 응답 여부) 하나뿐이다. 이것이 `acceptance.md` AC-IOS2-029가 요구하는 "두 값이 별개 필드" 이전의 상태이며, M2의 출발점이다.
- `portMapDeclared: false` — `EXPLORE_MOBILE_WDA_PORTS`가 선언돼 있지 않다. 이 호스트는 지금 기본 포트로 동작 중이다.
- §2.2에서 관측한 결함(기기가 `unavailable`이면 `wdaEnvironment` 자체가 안 나옴)이 여기서 대조된다 — **기기가 올라오니 나온다.** 즉 그 결함은 기기 상태에 종속된 갈래 문제이지 필드 누락이 아니다.
