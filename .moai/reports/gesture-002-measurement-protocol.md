# SPEC-GESTURE-002 사전 측정 절차서

작성일: 2026-08-25
상태: 실행 대기 (기기 복구 선행 필요)

## 이 문서의 목적

핀치(두 손가락 확대)와 더블탭의 **구현 가능 경로를 측정으로 확정한 뒤** SPEC을 쓴다.
추측으로 범위를 정하지 않는다 — 이 절차서의 결과가 SPEC-GESTURE-002의 Android 범위를 결정한다.

## 왜 측정이 먼저인가

2026-08-25 코드 조사에서 확인된 것:

- **iOS — 경로 있음.** `src/backend/wda-backend.ts:360` `performActions`가 W3C actions 봉투를
  한 곳에서 만든다. 현재 포인터 1개(`finger1`)만 싣는다. W3C 표준은 포인터를 여러 개 병렬로
  받으므로, 배열을 늘리면 멀티터치가 된다.
- **Android — 경로 미확인.** `src/backend/adb-backend.ts:368`이 `adb shell input tap`을 쓴다.
  `input` 명령에 멀티터치 서브명령이 있는지는 **확인되지 않았다.**

"Android는 멀티터치가 안 된다"는 현재 **가설이다.** 도구에 직접 물어보기 전에는 제약으로도
결함으로도 적지 않는다 (`.claude/rules/moai/core/verification-claim-integrity.md` §1.1).

## 범위 주의 — 이 절차서의 raw adb 호출에 대하여

아래 M-1~M-3은 `adb`를 직접 호출한다. 이것은 **explore-mobile CLI를 개발하기 위한 조사**이지,
CLI 사용 중에 adb로 우회해도 된다는 뜻이 **아니다.** 평상시 기기 조작은 explore-mobile 스킬의
제약대로 CLI만 통한다. 조사가 끝나면 여기서 확인된 능력은 CLI 명령으로 흡수된다.

## M-1. Android `input`이 멀티터치를 지원하는가

**가장 결정적이고 가장 싼 측정.** 도구에게 직접 물어본다.

```bash
adb -s <ANDROID_SERIAL> shell input
```

인자 없이 호출하면 지원하는 서브명령 목록(usage)을 출력한다.

**볼 것**: `tap` / `swipe` / `text` / `keyevent` 외에 멀티터치·포인터 관련 항목이 있는가.
특히 `motionevent`가 있으면 그 사용법에 포인터 인덱스 인자가 있는지 확인한다.

**판정**
- 멀티터치 경로 있음 → Android 핀치를 SPEC 범위에 **포함**
- 없음 → M-2로 진행

> 주의: 출력이 비어 있다고 "지원 안 함"으로 읽지 말 것. 명령이 usage를 stderr로 낼 수 있다.
> `2>&1`로 합쳐서 보고, 그래도 비면 `input --help`도 시도한다.
> **양성 대조**: 같은 방식으로 `adb -s <SERIAL> shell input tap 1 1`이 동작하는지 먼저 확인해
> adb 경로 자체가 살아있음을 증명한 뒤 판정한다.

## M-2. 터치스크린이 멀티터치를 보고하는가 (하드웨어 층)

```bash
adb -s <ANDROID_SERIAL> shell getevent -p 2>&1 | grep -i "ABS_MT\|SLOT\|TRACKING"
```

**볼 것**: `ABS_MT_SLOT`, `ABS_MT_POSITION_X/Y`, `ABS_MT_TRACKING_ID` 존재 여부.

**판정**
- 있음 → 드라이버 층에서는 멀티터치 가능. 단 **"adb로 쏠 수 있다"는 뜻은 아니다** — M-3 필요
- 없음 → 이 기기에서 멀티터치 주입은 불가. Android 핀치 **범위 제외 확정**

## M-3. `sendevent`로 이벤트를 주입할 권한이 있는가

```bash
adb -s <ANDROID_SERIAL> shell id
adb -s <ANDROID_SERIAL> shell ls -l /dev/input/
```

**볼 것**: 쉘 사용자가 `/dev/input/event*`에 쓰기 권한이 있는가 (보통 `root` 또는 `input` 그룹).

**판정**
- 쓰기 가능 → `sendevent` 방식 검토 가능. 단 **기기별 프로토콜이 달라 이식성이 낮다** —
  SPEC에서 이 취약성을 명시하고, 이 기기에서만 검증된 것으로 한정한다
- 불가 → 남는 길은 계측 APK뿐. 작업량이 크므로 **별도 SPEC으로 분리**하고
  SPEC-GESTURE-002에서는 `UNSUPPORTED_GESTURE_ON_ANDROID`로 정직하게 막는다

## M-4. 더블탭 — 인식 창 대 실제 호출 간격

오늘(2026-08-23 세션) 같은 좌표를 `tap`으로 2회 연속 호출했을 때 지도가 반응하지 않았다.
가설: **호출 간격이 더블탭 인식 창을 넘겼다.** 검증한다.

Android 기본 인식 창은 `ViewConfiguration.getDoubleTapTimeout()` = 300ms (기기별 상이 가능).

### M-4a. CLI 2회 연속 호출의 실제 간격

```bash
# 더블탭에 반응하는 화면(지도·사진 뷰어)을 띄운 상태에서
time ( node dist/cli/bin.js tap <X> <Y> --device <SERIAL> \
     && node dist/cli/bin.js tap <X> <Y> --device <SERIAL> )
```

**볼 것**: 총 소요 시간. 그리고 **화면이 실제로 확대됐는지 캡처로 확인한다** —
`ok:true`는 더블탭 인식의 증거가 아니다.

### M-4b. 한 번의 왕복으로 두 탭 (Android)

```bash
adb -s <ANDROID_SERIAL> shell "input tap <X> <Y>; input tap <X> <Y>"
```

프로세스 기동·왕복 비용을 한 번만 치른다. **판정은 캡처로 한다.**

### M-4c. 한 번의 요청으로 두 탭 (iOS)

W3C actions 한 요청 안에 `pointerDown → pointerUp → pause(약 60ms) → pointerDown → pointerUp`을
담는다. 기기가 순서를 직접 실행하므로 호스트 왕복 지연의 영향을 받지 않는다.
`performActions`를 그대로 쓰되 actions 배열만 바꿔 시험한다.

**판정**
- M-4a가 인식됨 → 더블탭은 **새 명령 없이** 문서 안내만으로 해결 가능 (가장 저렴)
- M-4a 실패 & M-4b/M-4c 성공 → **`doubletap` 명령 신설이 정당화됨** (한 왕복 안에 두 탭)
- 모두 실패 → 원인을 다시 진단한다. 간격 가설이 틀린 것이므로 새 가설이 필요하다

### M-1 — Android `input` 멀티터치 지원: **없음**

양성 대조 `adb shell echo` → `POSITIVE_CONTROL_OK` (경로 살아있음 확인 후 판정)

```
The commands and default sources are:
      text <string> (Default: touchscreen)
      keyevent [--longpress] <key code number or name> ... (Default: keyboard)
      tap <x> <y> (Default: touchscreen)
      swipe <x1> <y1> <x2> <y2> [duration(ms)] (Default: touchscreen)
      draganddrop <x1> <y1> <x2> <y2> [duration(ms)] (Default: touchscreen)
      press (Default: trackball)
      roll <dx> <dy> (Default: trackball)
      event <DOWN|UP|MOVE> <x> <y> (Default: touchscreen)
```

`event <DOWN|UP|MOVE> <x> <y>`가 있으나 **포인터 인덱스 인자가 없다** → 단일 손가락 전용.

### M-2 — 하드웨어 멀티터치: **지원 (10손가락)**

첫 시도에서 `grep -i "ABS_MT"`가 **0건**을 냈으나 이는 **오판이었다** — `getevent -p`는
능력을 이름이 아니라 16진 코드로 출력한다. 원문:

```
  name:     "sec_touchscreen"
    ABS (0003): 002f  : value 0, min 0, max 9, ...      <- ABS_MT_SLOT (슬롯 0..9)
                0035  : value 0, min 0, max 4095, ...   <- ABS_MT_POSITION_X
                0036  : value 0, min 0, max 4095, ...   <- ABS_MT_POSITION_Y
                0039  : value 0, min 0, max 65535, ...  <- ABS_MT_TRACKING_ID
```

핀치에 필요한 4개 코드가 모두 존재. 좌표계 주의: 터치 센서는 **X·Y 모두 0..4095**로 보고하며
화면 해상도(1080x2220)와 다르다 → 주입 시 환산 필요.

### M-3 — `sendevent` 주입 권한: **차단됨** (추론 실패 → 실행으로 정정)

`ls -l`은 `crw-rw---- system input`, `id`는 쉘이 `1004(input)` 그룹 소속 →
**"쓸 수 있다"고 추론했으나 실제 주입은 실패했다.**

```
sendevent: /dev/input/event0: Permission denied     (84개 이벤트 전량 실패)
```

원인은 파일 권한이 아니라 SELinux다. `getenforce` → `Enforcing`. 커널 감사 로그:

```
avc: denied { write } for pid=21712 comm="sendevent" name="event0"
  scontext=u:r:shell:s0 tcontext=u:object_r:input_device:s0
  tclass=chr_file permissive=0 SEPF_SM-G960N_10_0030
```

대조 실험: 같은 쉘에서 `input tap 1 1` → `TAP_OK`.
**adb 경로 자체는 정상이며, 막힌 것은 입력 장치 직접 쓰기 한 가지뿐이다.**

부작용 확인: 조작 전/후 캡처 40,424 → 40,391 bytes (시계 표시 차이 수준, 화면 변화 없음).

### M-4 — 더블탭 + iOS 핀치: **iOS 전량 성공** (2026-08-25, iPhone 15 Pro Max / iOS 26.6)

기기 복구: `doctor --yes` 1회로 기동됨 (`built:false, launched:true` — 기존 빌드 재사용).
`wda: reachable:true, controllable:"ok"` — 응답과 조작 권한을 **따로** 확인했다.

#### iOS 핀치 — **성공** (SPEC의 핵심 가정이 실기기에서 검증됨)

`POST /session/{id}/actions`에 포인터 **2개**(`finger1`/`finger2`)를 담아 전송.
각각 pointerMove → pointerDown → pause(120ms) → pointerMove(700ms, 바깥으로) → pointerUp.

응답 `{"value": null}` (오류 없음). **판정은 응답이 아니라 화면으로 했다**:
Apple 지도가 고덕역·배재고교가 보이던 축척에서 개별 가게명(한방누룽지통닭·스시혼·
CU 명일엘지점)이 읽히는 축척으로 **확대됨**. 캡처 111,935 → 117,774 bytes.

→ `wda-backend.ts:360` `performActions`의 단일 포인터 배열에 포인터를 추가하면 된다는
   구조 분석이 **실기기에서 확인됐다.** 코드 변경은 그 함수 중심으로 국소적이다.

#### 더블탭 — 원인 규명 완료

| 방식 | 두 탭 사이 간격 | 결과 |
|------|-----------------|------|
| A. CLI `tap` 2회 연속 호출 | **2,531 ms** | **실패** — 각각 독립된 단일 탭으로 처리 |
| B. 한 `actions` 요청에 down/up → pause(60ms) → down/up | 기기 내부 **60 ms** | **성공** — 더블탭 인식 |

방식 A의 관측: 지도가 확대되지 않고 가게("취향마라") 상세 패널이 열렸다 —
즉 **무반응이 아니라 단일 탭 두 번**이었다. 축척은 변하지 않았다(같은 가게들이 같은 크기).

방식 B의 관측: 지도가 확대되고 열려 있던 상세 패널이 닫혔다.

**원인 확정**: 더블탭 인식 창(약 250~300ms)에 비해 **CLI 왕복 2회가 약 10배 느리다.**
2026-08-23 세션에서 당근 지도의 더블탭이 듣지 않은 것은 이 지연 때문이며,
기기나 앱의 문제가 아니었다.

→ **`doubletap` 명령 신설이 정당화된다.** 두 탭을 **한 요청/한 왕복 안에** 담는 것이
   요건이며, 이는 `tap`을 두 번 부르는 것으로 대체할 수 없다.

#### M-4b (Android 더블탭) — **실패. 가설이 반증됐다**

대상: Chrome + 위키백과 표 (링크 아닌 빈 칸을 눌러 페이지 이동을 피함).
Google 지도는 첫 실행이 **약관 동의 화면**을 띄워 대상에서 제외했다 —
사용자를 대신해 약관에 동의하지 않는다.

| 방식 | 호스트 기준 소요 | 결과 |
|------|------------------|------|
| A. CLI `tap` 2회 | 1,256 ms | **실패** — 확대 없음 (글자 크기 동일) |
| B. `adb shell "input tap X Y; input tap X Y"` (왕복 1회) | 861 ms | **실패** — 육안 확인: 위키백과 표의 글자 크기·행 간격 동일, 확대 없음 |

> **기록 정정 (2026-08-25, M-5 이후)**: 이 표의 방식 B 칸은 원래 판정 근거로 바이트 델타
> (80,780 → 80,785)만 적고 있었다. 그러나 **실제로는 캡처를 열어 육안 판정했다** — 위키백과
> 인포박스가 같은 축척으로 그대로였다. M-5가 바이트 델타를 오라클에서 탈락시켰으므로 이 칸의
> 근거를 실제로 수행한 판정(육안)으로 정정한다. **증거를 추가한 것이 아니라, 수행하고도
> 적지 않은 판정을 기록한 것이다.** 따라서 방식 B의 실패 판정은 바이트에 의존하지 않으며,
> ⑦의 결론은 육안 판정 2건(방식 A·B) + 기기 내부 시간 측정(392 ms) 위에 선다.

**가설("왕복 1회면 창 안에 들어온다")은 틀렸다.** 기기 안에서 직접 잰 값:

```
1번째 tap 실행: 392 ms
2번째 tap 실행: 438 ms
두 탭 시작 간격: 392 ms
```

**원인은 왕복 횟수가 아니라 `input` 명령 자체의 기동 비용이다.** `input`은 호출마다
`app_process`(JVM)를 새로 띄우며 그것만으로 약 400 ms가 든다. 따라서 몇 개를 한 왕복에
묶든 탭 간격은 400 ms 아래로 내려가지 않으며, 이는 더블탭 인식 창(약 300 ms)을 넘는다.

iOS와 대비되는 지점: iOS는 **한 요청 안에 시퀀스를 기술하면 기기가 직접 실행**하므로
호스트 비용이 끼어들지 않는다(내부 간격 60 ms). Android `input`에는 그런 표현 수단이 없다.

**이식성 주의**: 400 ms는 이 기기(2018년 출시 Galaxy S9)의 값이다. 최신 기기는 더 빠를 수
있으나, **기기 속도에 좌우되는 동작을 기능으로 내놓는 것은 신뢰할 수 없다** — 어떤 기기에서는
되고 어떤 기기에서는 조용히 안 되는 결과가 된다.

→ **Android 더블탭도 핀치와 같은 결론**: `UNSUPPORTED_GESTURE_ON_ANDROID`.
   계측 APK SPEC이 두 기능을 함께 가져간다.

## M-5 — 핀치 지속시간 재측정 (2026-08-25, 감사 D1 대응)

**동기**: plan-auditor 1차 감사(0.77 FAIL)가 D1(critical)로 "성공을 만든 지속시간
(`pause 120ms` + `pointerMove 700ms`)이 SPEC에서 통째로 빠졌고, 그 결과 **모든 AC를 통과하면서
확대되지 않는 핀치**를 낼 수 있다"고 지적했다. 감사자는 실기기가 없어 이를 `scroll.ts`의
전례(`durationMs` 생략 → SSIM 1.000000, 전송됐으나 무동작)에서 **유추**했다.
사용자 판단으로 유추 대신 재측정을 택했다.

**조건**: iPhone 15 Pro Max / iOS 26.6, Apple 지도(원 측정과 동일 앱 — 앱을 바꾸면 제스처
인식기가 달라져 변수가 둘이 된다). 손가락 좌표·`pause(120ms)` 고정, `pointerMove` 지속시간만 변경.
확대/축소를 번갈아 수행해 지도가 한쪽 끝으로 밀리지 않게 했다.

### 결과 — 감사 D1의 구체적 실패 시나리오는 **반증됐다**

`pointerMove` 지속시간 **700 / 400 / 200 / 100 / 50 / 0 ms 전부에서 핀치가 동작했다.**
특히 **0 ms에서도 정상 동작**했으며, 이는 육안으로 두 번 확인했다:

- `in` 0 ms: 개별 가게가 보이던 축척 → 강동구·고속도로가 보이는 축척 (큰 축소)
- `out` 0 ms: 강동구 축척 → 개별 가게 축척 (큰 확대)

**iOS 핀치는 스와이프와 다르다.** 스와이프는 시간에 걸친 이동이 있어야 탭과 구별되지만,
핀치는 **두 손가락 사이 거리 변화 자체가 신호**여서 순간 이동도 인식된다.
따라서 `scroll.ts`의 전례를 핀치에 그대로 적용한 유추는 성립하지 않는다.

### 부수 결론 — **JPEG 바이트 크기는 화면 변화의 척도가 아니다**

이 측정에서 1차 판정 도구로 캡처 바이트 크기 변화율을 썼는데 **신뢰할 수 없었다**:
`ct_start` 121,235 → `ct_out0` 122,308 = **0.9%**였으나, 두 이미지는 **완전히 다른 축척**이었다
(구 단위 → 가게 단위). 서로 다른 그림이 우연히 비슷한 크기로 압축된 것이다.

따라서 이 절 상단 사다리 표에 기록했던 변화율(4.82% ~ 27.75%)은 **확대 폭의 척도가 아니며**,
"지속시간이 짧을수록 더 크게 확대된다"는 인상은 **근거 없는 인상이었다** — 철회한다.
의존성 0 원칙 아래 쓸 수 있는 이미지 비교 수단이 없으므로, **지속시간이 확대 폭에 미치는 영향은
미측정으로 남긴다.**

### SPEC에 대한 함의 (감사 D1을 그대로 이행하면 안 된다)

- 지속시간은 **명시되어야 한다.** 이유는 "안 그러면 동작하지 않아서"가 아니라
  **결정성** 때문이다 — 지속시간을 안 정하면 같은 `--amount`에 대해 구현마다 다른 결과가 나온다.
- **그러나 "지속시간이 0이면 실패한다"는 AC를 쓰면 안 된다.** 그것은 측정에 반하는 거짓 주장이다.
  감사가 제안한 형태의 AC를 그대로 넣었다면 **반증된 가정을 SPEC에 새겨 넣을 뻔했다.**
- 올바른 AC 형태: "지속시간이 이름 붙은 상수로 **명시적으로 전달되는가**"를 검사한다
  (값의 존재·출처를 보는 구조 검사), "0이면 확대가 실패하는가"(동작 주장)가 아니다.
- 참조값 `pointerMove 700ms` / `pause 120ms`는 **최초로 확대를 관측한 봉투의 값**이라는
  자격으로 기록한다 — 경계값도, 최적값도 아니다.

## SPEC-GESTURE-002 확정 범위 (측정 기반)

| 기능 | iOS | Android | 근거 |
|------|-----|---------|------|
| 핀치 (두 손가락 확대/축소) | **포함** — 실기기 검증 완료 | **제외** | iOS: 지도 확대 관측 / Android: SELinux가 주입 차단 (M-3) |
| 더블탭 | **포함** — 실기기 검증 완료 | **제외** | iOS: 한 요청 내 60 ms로 인식 / Android: `input` 기동 비용 392 ms > 인식 창 (M-4b) |

**두 기능 모두 v1은 iOS 전용이다.** 이것은 범위를 줄인 결정이 아니라 **측정 결과**다 —
Android는 두 기능이 서로 다른 이유로 막혔고(보안 정책 / 명령 기동 비용), 둘 다 우회로가
계측 APK 하나로 수렴한다.

**신설 명령**: `doubletap <x> <y>` — `tap` 2회 호출로 대체 불가능함이 양쪽 플랫폼에서 확정됨.
**신설 에러**: `UNSUPPORTED_GESTURE_ON_ANDROID` — 기존 `UNSUPPORTED_KEY_ON_IOS`와 대칭.
재시도해도 소용없음을 호출자가 즉시 알 수 있어야 한다.
**별도 SPEC으로 분리**: Android 계측 APK(UiAutomator) — 핀치와 더블탭을 함께 가져간다.
