# 구현 계획 — SPEC-IOS-002

## §A. 전제와 보존 대상

### A.1 착수 전 점검 (실행해 결과를 `progress.md`에 남긴다)

```bash
# 1. 기준선
git log -1 --format='%h %s'
git rev-list --count --left-right origin/master...HEAD    # 0 0 기대
pnpm test && pnpm typecheck && pnpm build                   # 전부 exit 0 기대

# 2. iOS 기기 현황 — 이 SPEC의 출발 상태
node dist/cli/bin.js devices

# 3. 외부 도구 존재 (command -v 단독으로 판정하지 않는다 — §A.4)
xcrun devicectl --version
xcodebuild -version
ls -l "$(brew --prefix 2>/dev/null)/bin/iproxy" 2>/dev/null || echo "iproxy: 경로 확인 필요"
```

2026-08-06 시점 관측: iOS 2대 모두 `connectionState: "unavailable"`. **이 SPEC은 그 상태에서 출발한다.**

### A.4 `command -v` 단독 판정 금지

`iproxy`의 존재 판정에 `command -v` 단독을 쓰지 않는다. `command -v`는 "PATH에서 실행 가능한가"를 묻지 "설치돼 있는가"를 묻지 않는다. 이 구분을 놓쳐 `adb`를 미설치로 오판한 이력이 있고 SPEC-READY-001이 그것을 닫았다 — **같은 실수를 iOS에서 반복하지 않는다.**

## §B. 닭과 달걀 — 조사가 자동화를 요구한다

**문제**: research.md §2의 조사(관문별 감지 신호)를 하려면 기기를 정상 상태로 만들었다가 관문을 하나씩 되돌려야 한다. 그런데 "정상 상태로 만들기"가 곧 이 SPEC이 자동화하려는 대상이다.

**해법**: M1에서 **손으로** 준비한다. 그리고 그 손 절차를 **명령·출력과 함께 기록**한다.

이 기록이 두 가지를 동시에 준다.

1. 조사에 필요한 정상 상태 — 관문을 되돌릴 출발점
2. **자동화가 재현해야 할 절차의 명세** — 손으로 밟은 순서가 곧 M4~M5가 코드로 옮길 대상이다

즉 M1은 조사이면서 동시에 요구사항 수집이다. 손 절차를 기록하지 않고 자동화부터 시작하면, 무엇을 자동화하는지 모르는 채 짜게 된다.

## §C. 마일스톤

### M1 — 조사: 손으로 준비하고, 관문을 되돌려 관측한다

**목표**: research.md §6의 산출물 요건 6개를 닫는다.

1. iOS 기기 1대를 손으로 정상 상태까지 올린다. **모든 명령과 출력을 기록한다.**
2. 관문을 하나씩 되돌리며 각 상태에서 관측한다 — `devicectl` 원본 JSON, `xcodebuild` 종료 코드·stderr, `iproxy` 연결 결과, WDA `/status`.
3. 두 기기(iPhone / iPad)에서 신호가 같은지 확인한다.
4. UDID가 세션을 넘어 안정적인지 확인한다.
5. `iproxy` 설치 판정 방법을 확정한다.
6. **서명 만료를 일반 실패와 가르는 신호를 찾는다**(`research.md` §6.1) — 종료 코드 → 구조화된 필드 → 자유 문구 순으로 확인하고, 셋 다 없으면 없다고 적는다. 만료 상태는 의도적으로 만들 수 없으므로(7일 대기) 이 항목은 기회 의존이며, 못 닫아도 착수를 막지 않는다.

**조사하지 않는 것**: `tunnelState`와 그 파생 문구(`unavailableReason`). 시점 종속 값임이 확인돼 후보에서 내렸다(`research.md` §2.3 · `progress.md` §E.1.1).

**산출**: `.moai/reports/ios-verification/SPEC-IOS-002-m1-<날짜>.md` — 명령과 출력 verbatim.

**코드 변경 없음.** 되돌릴 수 없는 관문이 있으면 **그 관문은 미조사로 기록**하고 다음으로 간다.

**이 마일스톤이 실패하면** — 파급은 M6 하나가 아니다:

- **M6(관문 감지)**: 조사 결과가 없으므로 "구분 불가"만 구현하고 끝낸다. 추측으로 진행하지 않는다(`design.md` §E.2).
- **M3 이후 사슬 전체**: M3가 전제하는 빌드 산출물이 없으므로 M3 → M4 → M5가 함께 막힌다(§D).
- **실기기 AC 12건 전부**: 기기 1대가 정상 상태로 올라오지 않으면 `e2e·manual` AC는 하나도 관측할 수 없다. 마일스톤별로는 M2 2건(AC-011 보조·012), M3 4건(AC-008·009·026·027), M4 3건(AC-005·006·007), M5 1건(AC-021), M6 1건(AC-020), M7 1건(AC-023)이다.
- **막히지 않는 것**: M2의 코드 작업, 그리고 **AC-028**(REQ-001의 실환경 판정) — 호스트 환경 변수만으로 판정되므로 iOS 기기가 필요 없다.

0.1.0은 여기에 *"관문 감지(M6)를 뺀 나머지로 범위를 줄인다"*고만 적어, M1 실패의 위험을 M6 하나로 축소해 보이게 했다. 실제 파급은 위와 같다.

### M2 — 설정 자리와 판정 근거 교체

**REQ-001 · REQ-004** — 서로 독립이지만 둘 다 외부 프로세스를 띄우지 않아 함께 묶는다.

- 설정 읽기 + 부재 시 전용 코드 실패 (AC-001~004)
- **실제 환경 변수를 세우고/지운 상태에서 설정 읽기를 판정한다 (AC-028)** — `process.env` mock으로 대체하지 않는다. iOS 기기가 필요 없으므로 기기 대기와 무관하게 닫을 수 있다
- 가용성 판정을 권한 요구 호출로 교체 (AC-010~012)
- `doctor` 출력에 러너 생존과 조작 가능성을 **따로** 싣는다 **(AC-029)** — 생존 2값 × 권한 3값(`design.md` §B.1.1)이 결과에서 구별돼야 한다

**왜 판정 교체가 앞인가**: 지금 코드가 고장 상태에서 "정상"을 답한다. 이후 마일스톤이 그 판정을 근거로 삼으므로, 틀린 판정 위에 자동화를 쌓으면 안 된다.

## §D. 마일스톤 간 의존

간선 목록이 이 절의 정본이다. 아래 7줄이 의존의 전부이며, 여기 없는 간선은 존재하지 않는다.

```
M1 (조사)       ──►  M3 (기동)         빌드 산출물
M1 (조사)       ──►  M6 (관문 감지)    조사 결과
M2 (설정·판정)  ──►  M3 (기동)         판정 근거
M3 (기동)       ──►  M4 (빌드)         기동이 빌드 성공의 확인 수단
M4 (빌드)       ──►  M5 (복구·만료)    재빌드 경로가 M4의 산출물
M5 (복구·만료)  ──►  M7 (문서·회귀)
M6 (관문 감지)  ──►  M7 (문서·회귀)

M1 ── M2 : 간선 없음 (어느 방향으로도 서로 독립)
```

0.2.0까지는 이 자리에 ASCII 그림이 있었으나 **그림이 아래 설명과 어긋나 있었다** — `M1 → M2`를 그려 두고(세로 화살표에 "(빌드 산출물)" 딱지가 붙어 있었다) 바로 아래 문단에서는 *"M1과 M2만 서로 독립이다"*라고 적었고, 실제로 있어야 할 `M1 → M3`는 글머리에만 있고 그림에는 없었으며, 아무 데서도 언급하지 않은 세로줄이 M7로 내려가고 있었다. 열을 세로로 읽어야 뜻이 정해지는 표현은 이렇게 조용히 어긋난다. 간선 목록으로 바꾼 이유가 그것이다.

- **M1 → M6**: 조사 없이 감지 규칙을 쓰지 않는다.
- **M1 → M3**: M3는 *"M1에서 빌드 산출물을 손으로 만들어 두었을 것"*을 전제로 하고 스스로 빌드하지 않는다(§C M3). 그 전제를 만드는 것이 M1이므로 이것은 실선 의존이다. 0.1.0의 그래프에는 이 간선이 빠져 있었다.
- **M2 → M3**: 기동 성공 판정이 M2의 판정 근거를 쓴다.
- **M3 → M4**: 빌드 성공을 조작 가능으로 확인하려면 기동이 먼저다.
- **M4 → M5**: M5의 만료 대응이 제시하는 재빌드 경로가 M4의 산출물이다(§F).
- **M7은 마지막**: 문서는 코드가 확정된 뒤에 맞춘다. M5와 M6 양쪽이 끝나야 들어간다.

**M1과 M2만 서로 독립이다** — M1이 막혀도 M2의 코드 작업은 진행할 수 있다(설정 읽기와 판정 근거 교체는 기기를 요구하지 않는다). 그러나 **M1이 막히면 M3 이후는 사슬로 함께 막힌다**: M3가 산출물을 못 받고, M4는 M3 뒤에 있고, M5는 M4 뒤에 있다. "M1과 M2가 독립이므로 M1 실패의 영향이 작다"고 읽으면 안 된다 — 독립인 것은 M2 하나뿐이고, 그것도 **코드 작업만** 독립이다(M2의 실기기 AC는 여전히 기기를 기다린다).

## §E. 검증 전략

### E.1 무엇을 unit으로, 무엇을 실기기로

| 성격 | 판정 |
|---|---|
| argv 구성, 분기, 오류 코드 선택, 재시도 횟수 | unit / unit(mock) |
| 외부 명령이 실제로 목적을 달성하는가 | **실기기 필수**(원칙 ⑤) |
| 사람 관문이 걸린 경로 | **실기기 + 관문 조작**(원칙 ⑥) |
| 문서와 코드의 일치 | doc-review |

### E.2 mock으로 판정했을 때 반드시 함께 적을 것

mock 판정 AC에는 **"이것은 argv 판정이며 동작 판정이 아니다"**를 명시한다. 이 문장이 없으면 mock PASS가 동작 PASS로 읽힌다 — mock은 argv 너머를 보지 못한다.

### E.3 미관측의 기록 방식

관측하지 못한 AC는 **미관측으로 기록**하고 PASS로 계상하지 않는다(원칙 ①). 미관측 사유를 적을 때는 **그 사유 자체가 검증 대상**임을 기억한다 — SPEC-READY-001에서 "사용자가 무선 디버깅을 켜야 한다"고 적은 차단 사유가 사실이 아니었던 이력이 있다.
