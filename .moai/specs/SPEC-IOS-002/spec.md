## §A. 개요 (Context & Goal)

### A.1 이 SPEC이 닫는 결함 — 준비 단계가 전부 수동이다

Android는 `doctor`가 환경을 진단하고, 동의를 받으면 `adb`를 설치하고, `text`가 필요할 때 IME를 스스로 내려받아 설치한다. **사용자가 손으로 밟는 단계가 없다.**

iOS는 정반대다. `WdaDoctor`는 진단만 하고 안내 문구를 낸다(`wda-doctor.ts:112` — *"안내만 한다 — 설치를 대신 수행하지 않는다"*). 실제로 iOS 명령 하나를 성공시키려면 사용자가 다음을 전부 손으로 밟아야 한다.

| # | 단계 | 자동화 가능? |
|---|---|---|
| 1 | 기기 개발자 모드 켜기 + 재시동 + 암호 | **불가** — 기기에서 사람이 |
| 2 | 개발자 인증서 신뢰(설정 → 일반 → VPN 및 기기 관리) | **불가** — 기기에서 사람이 |
| 3 | WDA 저장소 클론 | 가능 |
| 4 | `xcodebuild ... -allowProvisioningUpdates`로 빌드·설치 | 가능 |
| 5 | UI 자동화 승인(WDA 첫 기동 시 기기 암호) | **불가** — 기기에서 사람이 |
| 6 | `iproxy 8100:8100 -u <UDID>` 기동 | 가능 |
| 7 | `xcodebuild test-without-building`으로 러너 기동 | 가능 |
| 8 | 서명 만료(무료 계정 7일) 후 4~7 반복 | **부분 가능** — 재빌드·재설치는 자동, **UI 자동화 재승인은 사람** |

**8단계 중 4단계(3·4·6·7)가 완전 자동화 가능하고, 1단계(8)가 부분 자동화 가능한데, 지금은 전부 수동이다.**

8단계가 "가능"이 아니라 "부분 가능"인 이유는 이 표 자신 안에 있다. 8단계는 4~7의 반복이고 그 범위 안에 5단계(UI 자동화 승인)가 들어 있는데, 5단계는 같은 표에서 **불가 — 기기에서 사람이**로 적혀 있다. 그리고 이 SPEC의 조사 기록이 그 반복을 확인한다 — `research.md` §2.3: *"UI 자동화 승인 | 러너를 **재설치하면 재요구**"*. 즉 재빌드는 자동으로 끝나지 않고 **사람 관문 하나를 다시 세운다.**

그리고 자동화 불가능한 3개(1·2·5)는 지금 **구분되지 않는다** — 어느 관문에서 막혔든 사용자가 받는 것은 같은 `WDA_UNREACHABLE`과 같은 안내 문구다(`wda-errors.ts:33-34`).

### A.2 두 번째 결함 — "살아 있음" 판정이 거짓 양성을 낸다

`WdaDoctor.checkWda()`는 `GET /status`의 성공을 도달 가능(`reachable: true`)의 근거로 쓴다(`wda-doctor.ts:104-106`). 그런데 2026-08-03 실측에서 **러너가 오래 떠 있으면 `/status`는 200인데 조작 계열만 500으로 실패**하는 상태가 관측됐다(`XCTDaemonErrorDomain Code=41`, "Not authorized for performing UI testing actions"). 화면 잠금이 원인이 아니다(`/wda/locked` → `false`).

즉 **`doctor`가 "정상"이라고 말한 직후 `screenshot`이 실패**할 수 있다. 그 회차에 실제로 코드 회귀를 의심해 시간을 썼다.

복구는 싸다 — 기존 `iproxy`를 그대로 두고 러너만 다시 띄우면 **약 6초**에 복구되며 재빌드가 필요 없다.

### A.3 목표

1. 완전 자동화 가능한 4단계(3·4·6·7)를 CLI가 수행한다. 부분 자동화 가능한 8단계(만료 후 반복)는 재빌드·재설치까지 CLI가 하고, **그 뒤의 UI 자동화 재승인은 사람에게 남긴 채 그 사실을 보고한다.**
2. 자동화 불가능한 3단계(1·2·5)를 **각각 구분해** 보고한다 — "지금 몇 번에서 막혔는가"에 답한다.
3. "살아 있음" 판정을 조작 가능성 기준으로 바꾼다.
4. 권한 상실을 1회 재기동으로 자동 복구한다.
5. 띄운 백그라운드 프로세스의 소유권과 종료 경로를 명시한다.

### A.4 목표가 아닌 것

- **iOS 시뮬레이터** — `devicectl`이 실기기만 열거한다는 기존 결정 유지(SPEC-READY-001 §D.2 계승).
- **유료 개발자 계정 전제** — 무료 개인팀의 7일 만료를 1급 사례로 다룬다. 유료 계정을 요구하지 않는다.
- **새 기기 제어 기능** — 이 SPEC은 기존 명령을 **쓸 수 있게 만드는 것**만 다룬다. `tap`/`text`/`screenshot`의 동작은 무변경.
- **Android 경로 변경** — `doctor`의 Android 분기와 IME 세션 처리는 손대지 않는다.
- **WDA 자체 포크·수정** — 상류 WebDriverAgent를 그대로 쓴다.

## §B. 요구사항 (REQ)

### REQ-IOS2-001 — 사용자별 빌드 설정을 선언된 자리에서 읽는다

**Where** iOS 빌드가 필요한 값(Apple 개발팀 식별자, 번들 식별자, WDA 소스 위치)이 사용자마다 다르고, **When** CLI가 빌드를 수행할 때, **the system shall** 그 값들을 **선언된 단일 위치**에서 읽고, 없으면 **무엇을 어디에 적어야 하는지** 지목해 실패한다.

- 추측 금지: 개발팀 식별자를 키체인·Xcode 설정에서 유추하지 않는다. 잘못 유추하면 남의 팀으로 서명을 시도한다.
- 값이 없을 때의 실패는 `WDA_UNREACHABLE`이 아니라 **설정 부재를 지목하는 별도 코드**여야 한다 — 두 실패의 복구 절차가 전혀 다르다.

### REQ-IOS2-002 — 빌드를 CLI가 수행한다

**Where** 설정이 갖춰져 있고 **When** 사용자가 빌드를 요청하면, **the system shall** WDA 소스를 확보하고 `xcodebuild`로 기기에 설치하며, **표준 출력이 아니라 구조화된 결과**로 성공/실패를 보고한다.

- 빌드 산출물(`.xctestrun`)의 위치를 이후 기동이 찾을 수 있는 **결정적인 자리**에 남긴다.
- 빌드는 오래 걸린다 — 진행 중임을 알 수 있어야 하고, 실패 시 `xcodebuild`의 원인 줄을 잃지 않아야 한다.

### REQ-IOS2-003 — 포트 연결과 러너 기동을 CLI가 수행한다

**Where** 빌드 산출물이 존재하고 **When** 사용자가 기동을 요청하면, **the system shall** 포트 포워딩과 러너를 띄우고, **조작이 실제로 가능해질 때까지 기다린 뒤** 성공을 보고한다.

- "프로세스를 띄웠다"를 성공으로 보고하지 않는다 — 조작 가능 확인까지가 성공이다(REQ-IOS2-004의 판정을 쓴다).
- 이미 떠 있으면 중복 기동하지 않는다.

### REQ-IOS2-004 — "쓸 수 있음"은 조작 계열로 판정한다

**Where** WDA의 가용성을 판정할 때, **the system shall** `GET /status`의 성공만으로 가용하다고 판정하지 **않고**, 조작 권한이 실제로 살아 있음을 보이는 검사를 근거로 삼는다.

- **판정 근거의 성격 변화가 이 요구사항의 핵심이다.** `/status` 200은 러너 생존만 말하며 UI 테스팅 권한을 보장하지 않는다(§C.2).
- 검사는 **화면을 바꾸지 않아야 한다** — 판정 자체가 기기 상태를 바꾸면 측정이 조작이 된다.
- `doctor`의 기존 출력 형태를 깨지 않는다(REQ-IOS2-008).

### REQ-IOS2-005 — 권한 상실을 1회 재기동으로 복구한다

**Where** 조작 명령이 권한 오류로 실패하고 **When** 그 원인이 러너 권한 상실로 판정되면, **the system shall** 러너를 **1회** 다시 띄우고 원래 명령을 **1회** 재시도한다.

- **재시도는 1회로 제한한다.** 무한 반복은 복구가 아니라 죽음의 고리다.
- 재기동으로 복구했다는 사실을 **결과에 남긴다** — 조용히 성공하면 사용자는 러너가 불안정하다는 것을 영원히 모른다.
- 재기동해도 실패하면 원래 오류를 그대로 돌려준다. 재기동 실패로 원인을 덮지 않는다.
- **조작 명령의 재시도 안전성**은 별개 문제다 — 응답을 잃은 변경 계열 호출은 재시도하지 않는다(§C.3).

### REQ-IOS2-006 — 사람이 해야 하는 관문 3개를 구분해 보고한다

**Where** iOS 준비가 완료되지 않았고 **When** 사용자가 진단을 요청하면, **the system shall** 개발자 모드·인증서 신뢰·UI 자동화 승인 중 **어느 것이 미충족인지 구분해** 보고한다.

- 셋을 하나의 "WDA를 띄우세요"로 뭉치지 않는다. 사용자가 밟아야 할 화면이 서로 다르다.
- **구분 근거는 실측으로 확보한다** — 각 관문 미충족 시의 관측 가능한 신호를 실기기에서 확인하기 전에는 감지 규칙을 확정하지 않는다(§C.0, research.md).
- 구분이 불가능한 관문이 있으면 **구분 불가임을 그대로 보고한다.** 추측한 구분을 사실처럼 말하지 않는다.

### REQ-IOS2-007 — 서명 만료를 감지하고 재빌드 경로를 준다

**Where** 무료 개인팀 서명이 만료되어 러너 기동이 실패할 때, **the system shall** 그 실패를 **만료로 식별**하고 재빌드 경로를 제시한다.

- 만료 실패를 일반 기동 실패와 같은 문구로 내면 사용자는 원인을 못 찾는다.
- 재빌드는 REQ-IOS2-002의 경로를 재사용한다 — 별도 경로를 만들지 않는다.
- **재빌드로 끝나지 않는다.** 제시하는 경로는 재빌드 뒤에 **UI 자동화 재승인(§A.1 5단계)이 다시 필요할 수 있음**을 함께 알려야 한다. 러너를 재설치하면 그 승인이 재요구된다(`research.md` §2.3). 재빌드만 안내하면 사용자는 자동으로 끝나는 줄 알고 기다리다가 기기에서 뜬 승인 창을 놓친다.
- **구별 근거는 실측으로 확보한다** — 만료를 일반 실패와 가르는 관측 신호를 확인하기 전에는 식별 규칙을 확정하지 않는다(§E.2, `research.md` §6.1).

### REQ-IOS2-008 — 기존 계약에 회귀를 만들지 않는다

**Where** 이 SPEC이 `doctor`·오류 코드·`devices`의 출력을 건드릴 때, **the system shall** 기존 소비자가 읽던 필드와 값의 의미를 **바꾸지 않거나, 바꾼다면 그 사실을 계약 문서와 테스트 양쪽에 반영**한다.

- 특히 `connectionState: "unavailable"` + `unavailableReason`(SPEC-READY-001 REQ-READY-003)의 의미를 유지한다.
- `WdaDoctor.checkDevicectl`(백엔드 가용성 게이트)과 `checkWda`(제어 가능 여부)의 분리를 유지한다 — 합치면 WDA 미기동 시 연결된 iOS 기기가 `devices` 목록에서 통째로 사라진다(`wda-doctor.ts:10-16` @MX:WARN).
- `SKILL.md`의 iOS 절을 코드와 일치시킨다.

### REQ-IOS2-009 — 띄운 프로세스의 소유권과 종료 경로를 정한다

**Where** CLI가 포트 포워딩과 러너를 백그라운드로 띄웠을 때, **the system shall** 그 프로세스들의 **소유자와 종료 방법**을 명시하고, 사용자가 정리할 수 있는 경로를 제공한다.

- 띄우고 잊으면 다음 세션에서 유령 프로세스와 포트 점유가 남는다.
- iOS `reset`이 지금 no-op이라는 계약(`wda-doctor.ts:132-141`)과의 관계를 정해야 한다 — 이 SPEC이 상태를 만든다면 `reset`은 더 이상 no-op이 아닐 수 있다.

## §C. 관측 근거

### C.0 이 절의 근거는 재확인 대상이다

아래 §C.1~§C.3은 **2026-08-02 / 2026-08-03 관측 기록**에서 인용한 것이며, 이 SPEC 착수 시점(2026-08-06)에 **재확인되지 않았다.**

- 2026-08-06 현재 이 호스트의 iOS 기기 2대는 모두 `connectionState: "unavailable"`이다(오늘 `devices` 실행으로 직접 확인). 즉 §C.1의 "동작한다" 기록을 지금 재현할 수 없는 상태다.
- 관측값이 몇 시간 만에도 낡는다는 것은 이 저장소가 이미 기록한 교훈이다.

**따라서 run-phase는 §C의 인용값을 그대로 신뢰하지 않고, 각 값을 착수 시점에 재측정한다**(acceptance.md 원칙 ①).

### C.1 전 경로가 동작한 기록 (2026-08-02)

iPhone16,2 / iOS 26.5.2, USB, Xcode 26.0, 무료 개인팀.

| 기능 | 경로 | 기록된 값 |
|---|---|---|
| 화면 캡처 | WDA `GET /screenshot` | 111ms |
| 좌표 탭 | WDA `POST /session/:id/actions` | 약 480ms |
| 텍스트 입력 | WDA `/wda/keys` | 한글·이모지 동작 |

이 기록의 의미는 **"준비만 되면 제어는 이미 동작한다"**는 것이다. 이 SPEC이 여는 것은 제어가 아니라 **준비**다.

### C.2 러너가 권한을 잃는다 (2026-08-03, 약 14시간 가동 후)

| 호출 | 결과 |
|---|---|
| `GET /status` | **200**, `ready: true` |
| `GET /screenshot` | **500** — "Not authorized for performing UI testing actions" |
| `GET /wda/locked` | `false` — 화면 잠금이 원인이 아니다 |

더 지나면 `/status`도 응답하지 않게 된다. **재기동 약 6초로 복구**되며 재빌드는 불필요했다.

이것이 REQ-IOS2-004(판정 근거 교체)와 REQ-IOS2-005(1회 재기동)의 직접 근거다.

### C.3 변경 계열 호출은 응답을 잃는다

같은 기간 기록: 앱 종료 4/4, 탭 1/5에서 **응답이 유실됐는데 효과는 적용됐다.** 즉 "응답이 없다"가 "적용되지 않았다"를 뜻하지 않는다.

이 사실이 REQ-IOS2-005의 경계를 정한다 — **재기동 후 재시도는 조작 명령 자체의 재시도를 정당화하지 않는다.** 이미 `WDA_RESPONSE_LOST`가 이 구분을 계약에 담고 있다(`SKILL.md` 오류 코드 표).

### C.4 지금 코드가 서 있는 자리 (2026-08-06 확인)

- `src/backend/wda-doctor.ts` — `checkDevicectl` / `checkWda` / `installGuidance` / `resetDevice`. 진단과 **안내만** 한다.
- `src/backend/wda-errors.ts:33-34` — 복구 안내가 `iproxy`와 `xcodebuild` 두 줄을 문자열로 제시한다. **관문 3개를 구분하지 않는다.**
- `src/backend/wda-client.ts` — HTTP 계층. `WDA_UNREACHABLE` / `WDA_RESPONSE_LOST` / `WDA_COMMAND_FAILED`를 구분한다.
- SPEC-READY-001 §D.2가 이 작업을 명시적으로 범위 밖으로 선언했다.

## §E. 설계 결정 (요약)

자세한 논거와 기각된 대안은 `design.md`에 있다. 여기에는 결론만 적는다.

### E.1 판정 근거를 바꾸되 `/status`를 버리지는 않는다

`/status`는 **러너 생존**의 신호로 계속 쓴다. 다만 그것만으로 "쓸 수 있음"을 주장하지 않는다. 생존과 권한은 다른 질문이며, §C.2가 그 둘이 갈라지는 상태를 실제로 보였다.

### E.2 관문 감지와 만료 식별은 실측 전에는 확정하지 않는다

REQ-006의 감지 규칙은 **research.md의 조사가 끝나기 전에 코드로 쓰지 않는다.** 근거 없이 규칙을 쓰면 틀린 안내를 사실처럼 말하게 되고, 그것은 이 저장소가 이미 한 번 겪은 실패 형태다(오류 문구에서 정책을 역추론했다가 반증된 이력).

**REQ-007의 만료 식별 규칙에도 같은 봉인을 건다.** 만료를 일반 기동 실패와 가르는 신호가 무엇인지 아직 모른다 — 종료 코드인지, 구조화된 필드인지, 자유 문구뿐인지. 조사(`research.md` §6.1)가 답하기 전에는 규칙을 코드로 쓰지 않는다.

봉인이 필요한 이유가 REQ-006보다 오히려 뚜렷하다. 봉인이 없으면 구현자는 손에 잡히는 유일한 재료인 `xcodebuild`의 오류 문구를 읽어 규칙을 만들게 되고, 그것이 정확히 이 SPEC이 §C.4에서 경계하는 실패 형태다. 조사가 종료 코드나 구조화된 필드를 찾지 못하면 **문구 기반 판정임을 명시된 한계로 적은 뒤** 쓰거나, 아예 "구별 불가"로 좁혀 마감한다.

### E.3 자동 복구는 1회로 묶는다

재시도 상한을 1회로 두는 것은 성능이 아니라 **관측 가능성** 때문이다. N회 재시도는 실패를 지연시키고 원인을 흐린다. 1회로 묶으면 "재기동으로 복구되는 문제"와 "그렇지 않은 문제"가 즉시 갈린다.

### E.4 이 SPEC이 검증 방법에 두는 제약

- 외부 CLI(`xcodebuild`, `iproxy`, `xcrun`)를 호출하는 경로는 **mock 단독으로 판정하지 않는다.** mock은 argv 너머를 보지 못한다.
- 사람 관문이 걸린 경로는 **실기기에서 그 관문을 실제로 미충족 상태로 만들어** 관측한다. 만들 수 없으면 **미관측으로 기록**하고 PASS로 올리지 않는다.
- 시간이 지나야 나타나는 상태(권한 상실)는 재현이 어렵다 — 재현할 수 없으면 그 사실을 적는다.
