# 조사 — SPEC-IOS-002

이 문서는 **아는 것과 모르는 것을 가르는** 데 쓴다. §2가 이 SPEC의 가장 큰 미지이며, §2를 닫기 전에는 REQ-IOS2-006의 감지 규칙을 코드로 쓰지 않는다(spec.md §E.2).

---

## §1. 지금 코드가 iOS에 대해 하는 일 (2026-08-06 확인)

### 1.1 파일 배치

| 파일 | 역할 |
|---|---|
| `src/backend/wda-doctor.ts` | 환경 진단 4종 — `checkDevicectl` / `checkWda` / `installGuidance` / `resetDevice` |
| `src/backend/wda-client.ts` | WDA HTTP 계층. 포트 해석, 오류 3종 구분 |
| `src/backend/wda-errors.ts` | `WDA_UNREACHABLE` / `WDA_RESPONSE_LOST` / `WDA_PORT_UNMAPPED` + 복구 안내 문구 |
| `src/backend/wda-device-list.ts` | `devicectl` 기반 기기 열거, `connectionState` 판정 |
| `src/backend/wda-backend.ts` | 제어 명령의 iOS 구현 |
| `src/cli/commands/doctor.ts` | iOS 대상일 때 `wdaEnvironment: { devicectl, wda }`를 싣는다 |

### 1.2 이미 잡혀 있는 것

- **가용성 게이트와 제어 가능성의 분리.** `checkDevicectl`(Xcode 있나)과 `checkWda`(WDA 뜨나)가 의도적으로 분리돼 있고, `wda-doctor.ts:10-16`의 `@MX:WARN`이 합치지 말라고 못 박는다. 합치면 WDA 미기동 시 iOS 기기가 `devices`에서 통째로 사라진다.
- **포트 매핑 선언 여부의 노출.** `WdaCheck.portMapDeclared`가 기본 포트를 쓰고 있다는 사실을 보고서에 드러낸다.
- **응답 유실과 도달 불가의 구분.** `wda-client.ts:222` 주석이 이 둘을 섞으면 "WDA를 다시 띄우라"는 엉뚱한 복구 절차를 내놓게 된다고 적고 있다.

### 1.3 없는 것

- 빌드·기동을 **수행**하는 코드 (전무 — 안내 문구만 있다)
- 사용자별 빌드 설정을 읽는 자리
- 빌드 산출물의 위치 규약
- 백그라운드 프로세스의 소유·종료 경로
- 관문별 감지

### 1.4 대조군 — Android는 어디까지 하는가

Android 경로는 동의를 받아 `adb`를 설치하고(`doctor --yes`, Homebrew, macOS 한정), `text`가 필요할 때 IME APK를 스스로 내려받아 설치한다. **자동 설치 자체는 이 저장소가 이미 하는 일이고, 동의 규칙도 이미 있다.** iOS만 "안내만 한다"에 머물러 있다.

→ 설계 시사: 동의 모형을 새로 발명할 필요가 없다. Android가 쓰는 명시적 동의 규칙을 iOS에 적용할 수 있는지가 design.md의 질문이다.

## §2. 가장 큰 미지 — 관문 3개를 어떻게 구분하는가

### 2.1 무엇을 모르는가

사람이 기기에서 해야 하는 관문 3개가 **각각 미충족일 때 호스트에서 관측되는 신호가 무엇인지 모른다.**

| # | 관문 | 미충족 시 관측되는 신호 | 상태 |
|---|---|---|---|
| 1 | 개발자 모드 꺼짐 | ? | **미조사** |
| 2 | 개발자 인증서 미신뢰 | ? | **미조사** |
| 3 | UI 자동화 미승인 | 60초 후 `Timed out while enabling automation mode` (기록됨, 재확인 필요) | **부분** |

3번만 기록에 문구가 남아 있고, 그것도 2026-08-02 기록이라 재확인이 필요하다.

### 2.2 왜 추측하면 안 되는가

이 저장소는 **오류 문구에서 정책을 역추론했다가 반증된 이력**이 있다. 문구는 도구 버전에 따라 바뀌고, 같은 문구가 서로 다른 원인에서 나올 수 있다. 관문 감지는 사용자에게 **"설정의 이 화면으로 가라"**고 지시하는 기능이므로, 틀린 감지는 사용자를 엉뚱한 화면으로 보낸다.

### 2.3 어떻게 알아낼 것인가

관문을 하나씩 미충족 상태로 만들고 관측한다. **각 관문은 되돌릴 수 있어야 조사가 가능하다.**

| 관문 | 미충족 상태로 만드는 법 | 되돌리기 | 위험 |
|---|---|---|---|
| 개발자 모드 | 설정에서 끄기 | 다시 켜기(재시동 필요) | 낮음 — 되돌아감 |
| 인증서 신뢰 | 설정에서 신뢰 해제 | 다시 신뢰 | 낮음 |
| UI 자동화 승인 | 러너를 재설치하면 재요구 | 승인 | 중간 — 재빌드 필요할 수 있음 |

각 상태에서 관측할 대상:

- `xcrun devicectl list devices` 원본 JSON의 필드 (특히 `connectionProperties` / `deviceProperties`)
- `xcodebuild test-without-building`의 종료 코드와 stderr
- `iproxy` 연결 성공 여부
- WDA `/status`의 응답 여부와 내용

**후보에서 내린 것 — `tunnelState`와 그 파생 문구(`unavailableReason`)**

한때 이것이 관문을 가르는 신호일 수 있다고 보았다. 두 기기의 사유 문구가 서로 달랐기 때문이다(2026-08-06 측정). 하루 뒤 같은 명령을 다시 돌리자 **두 기기가 같은 문구를 냈다**(2026-08-07 측정, `progress.md` §E.1.1에 두 측정을 나란히 기록).

**시점 종속 값이므로 후보에서 제외한다.** 기기 구성을 바꾸지 않았는데 값이 바뀌었으므로, 이 값의 차이는 기기나 관문 상태를 가리키지 않는다. 같은 성질을 SPEC-READY-001이 먼저 기록했다(`progress.md:152` — *"같은 기기의 값이 하루 안에 바뀐다"*).

M1은 이 항목을 조사하지 않는다. 조사해도 얻을 것이 없고, 그 위에 감지 규칙을 세우면 하루 만에 낡는다.

### 2.4 조사가 실패할 수 있는 경로

- **구분 불가일 수 있다.** 서로 다른 관문이 같은 신호를 낼 수 있다. 그 경우 REQ-IOS2-006은 "구분 불가"를 그대로 보고하는 것으로 충족된다 — 구분한 척하지 않는다.
- **기기 모델·iOS 버전에 따라 다를 수 있다.** 이 호스트에는 iPhone 15 Pro Max와 iPad Pro가 있다. 두 대에서 신호가 다르면 그 사실 자체가 결과다.
- **지금 조사할 수 없다.** 2026-08-06 현재 두 기기 모두 `unavailable`이다. 조사는 최소 한 대를 정상 상태로 만든 뒤에야 시작할 수 있고, 그 "정상 상태로 만들기"가 곧 이 SPEC이 자동화하려는 대상이다 — **닭과 달걀이다.**

→ 이 순환은 계획에 반영해야 한다(plan.md).

## §3. 두 번째 미지 — 권한 상실의 재현

### 3.1 아는 것

2026-08-03 기록: 러너 약 14시간 가동 후 `/status` 200 / 조작 500. 재기동 약 6초로 복구.

### 3.2 모르는 것

- **언제 잃는가.** 14시간은 한 번의 관측이지 임계값이 아니다.
- **무엇이 방아쇠인가.** 시간인지, 화면 잠금 횟수인지, 다른 요인인지 모른다. `/wda/locked`가 `false`였다는 것은 "그 순간 잠겨 있지 않았다"만 말한다.
- **재현 가능한가.** 자동 복구(REQ-IOS2-005)를 검증하려면 권한 상실 상태를 만들어야 하는데, 14시간을 기다리는 것은 검증 절차가 될 수 없다.

### 3.3 검증 우회 후보

- 러너를 강제 종료한 뒤 조작 → 이것은 **권한 상실이 아니라 도달 불가**다. 다른 상태를 검증하게 된다.
- WDA에 권한 오류를 흉내내는 응답을 주입 → mock 경로. §E.4의 "mock 단독 판정 금지"에 걸린다.
- 실제 상실을 기다렸다가 그 순간 검증 → 재현 불가, 기회 의존.

→ **결론 없음.** 이 항목은 acceptance.md에서 "실환경 판정이 어려운 AC"로 명시하고, 만들 수 없으면 미관측으로 남긴다.

## §4. 세 번째 미지 — 백그라운드 프로세스 소유권

### 4.1 문제

`iproxy`와 러너는 **CLI 프로세스보다 오래 살아야** 한다. CLI는 명령 하나를 처리하고 종료하는데, 그 다음 명령이 같은 러너를 써야 하기 때문이다.

### 4.2 후보와 각각의 미지

| 후보 | 미지 |
|---|---|
| 띄우고 놔둔다(detach) | 다음 세션이 그 프로세스를 어떻게 찾는가? 살아 있는지 어떻게 아는가? |
| CLI가 관리한다(start/stop 명령 추가) | 상태를 어디에 저장하는가? 저장소가 낡으면? |
| 매 명령마다 띄우고 끈다 | 러너 기동이 6초 — 명령당 6초는 수용 불가 |

### 4.3 이 저장소에 이미 있는 유사 문제

IME 세션 저장소(`src/backend/ime-session-store.ts`)가 **기기별 상태를 디스크에 남기는** 같은 형태의 문제를 이미 푼다. 그리고 그 저장소가 남긴 교훈이 있다 — **무선 시리얼을 영속 키로 쓰면 재연결 후 조회가 빗나간다.**

iOS는 전송이 하나뿐이라 시리얼이 안정적일 가능성이 높지만, **확인된 사실이 아니다.** `devicectl`의 식별자와 `iproxy -u`가 쓰는 UDID가 다르다는 것은 이미 기록돼 있다.

→ 설계 시사: 상태를 남긴다면 키는 **UDID**여야 하고, 그 UDID가 세션을 넘어 안정적인지 먼저 확인해야 한다.

## §5. 외부 도구 의존

| 도구 | 제공 | 이미 쓰는가 | 비고 |
|---|---|---|---|
| `xcrun devicectl` | Xcode | 예 | 기기 열거. JSON은 stdout이 아니라 파일로 나온다 |
| `xcodebuild` | Xcode | 아니오 | 빌드·러너 기동 양쪽에 쓰인다 |
| `iproxy` | `libimobiledevice` (Homebrew) | 아니오 | 안내 문구에만 등장 |
| WebDriverAgent | GitHub (appium) | 예(런타임) | 소스를 받아 빌드해야 함 |

**설치 여부 판정 시 주의**: `command -v`는 "PATH에서 실행 가능한가"를 묻지 "설치돼 있는가"를 묻지 않는다. 이 구분을 놓쳐 `adb`를 미설치로 오판한 이력이 있고, SPEC-READY-001이 그것을 닫았다. **`iproxy`에 같은 실수를 반복하지 않는다.**

## §6. 조사 산출물 요건

이 조사가 끝났다고 말하려면 다음이 있어야 한다.

1. 관문 3개 각각의 미충족 신호 — 관측된 원본 출력과 함께. 구분 불가면 그 사실.
2. 두 기기(iPhone / iPad)에서 신호가 같은지 다른지.
3. UDID가 세션을 넘어 안정적인지.
4. `iproxy` 설치 판정 방법 — `command -v` 단독이 아닌 것.
5. 권한 상실을 의도적으로 만들 방법이 있는지 — 없으면 없다고.
6. **서명 만료를 일반 기동 실패와 가르는 신호가 무엇인지** — REQ-IOS2-007의 근거.

### 6.1 서명 만료 신호 조사가 별도 항목인 이유

REQ-IOS2-007은 "만료를 일반 실패와 **구별**한다"고 요구하는데, **무엇을 보고 구별하는지가 정해져 있지 않다.** 관문 감지(§2)와 같은 성질의 미지인데 §6에 항목이 없어서 조사 대상에서 빠져 있었다.

조사할 것:

- `xcodebuild test-without-building`이 만료 상태에서 내는 **종료 코드**가 정상 실패와 다른가.
- `xcodebuild`가 구조화된 출력(`-resultBundlePath`의 결과 번들, `-json` 계열)으로 만료를 표시하는가.
- `devicectl`이 설치된 앱의 서명 만료를 별도 필드로 드러내는가.
- 위 셋이 전부 없고 **자유 문구만 남는다면** 그 사실을 그대로 적는다.

**문구를 정책으로 삼지 않는다.** 이 저장소는 오류 문구에서 정책을 역추론했다가 반증된 이력이 있다(§2.2와 같은 근거). 종료 코드나 구조화된 필드가 있으면 그것을 쓰고, 자유 문구뿐이면 "문구 기반 판정은 도구 버전에 종속된다"를 **명시된 한계로 기록한 뒤** 그 위에서 구현한다.

이 항목이 닫히지 않아도 착수는 가능하다 — 만료 식별이 불가능하면 REQ-007은 "구별 불가"를 그대로 보고하는 것으로 좁혀 마감한다. 관문 감지(§2)와 같은 처리다.
