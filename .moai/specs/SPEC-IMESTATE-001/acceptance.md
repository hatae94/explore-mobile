# 인수 기준 — SPEC-IMESTATE-001

> 형식: Given-When-Then. 각 AC는 관찰 가능(테스트 출력 / 파일 존재 / 필드 검증 / 명령 출력)해야 한다. 검증 방식은 unit / unit(mock) / unit(실FS) / greppable / git(범위 비교) / e2e(호스트) / e2e·manual / doc-review 중 하나 이상을 명시한다.
>
> **원칙(SPEC-IOS-001에서 확립)**: 관측하지 않은 것을 PASS로 기록하지 않는다.
>
> **이 SPEC 고유의 원칙 ①**: AC-002는 **수정 전에 FAIL이 관측되어야** 이후의 PASS가 의미를 갖는다. 수정 전 FAIL 관측 기록이 없으면 PASS로 인정하지 않는다.
>
> **이 SPEC 고유의 원칙 ② (0.2.0 — 감사 반영)**: "없음"을 확인하는 검사는 **양성 대조를 동반**해야 한다. 패턴이 틀려서 아무것도 매치하지 않는 것과 대상이 깨끗한 것을 구별할 수 없는 검사는 공허하다. 1차 감사에서 AC-008(grep 패턴이 실제로 매치되지 않음)과 AC-018(`git diff`가 커밋 후 항상 빈 출력)이 이 함정에 빠졌고, 둘 다 REQ 보호의 **유일한** 기계적 증거였다.

### AC-IMESTATE-001 — 서로 다른 시리얼은 서로 다른 파일을 쓴다
- **Given** 빈 캐시 디렉터리와 서로 다른 시리얼 `SERIAL-A` · `SERIAL-B`,
- **When** 두 시리얼에 대해 각각 `setOriginalIme`을 수행하면,
- **Then** 두 기록이 **서로 다른 경로**에 저장되고, `getOriginalIme("SERIAL-A")`와 `getOriginalIme("SERIAL-B")`가 **모두** 각자 기록한 값을 반환한다.
- 검증: unit

### AC-IMESTATE-002 — 인터리빙을 강제해도 시리얼 간 기록이 유실되지 않는다 (핵심 AC)
- **Given** 아래 두 요건을 만족하는 테스트 하네스와 서로 다른 시리얼 2개,
- **When** `setOriginalIme` 두 호출의 **내부 읽기가 둘 다 끝난 뒤에야 쓰기가 일어나도록** 강제하면,
- **Then** 두 시리얼의 기록이 **모두** 조회된다.

**하네스 요건 (필수 — 0.2.0 감사 반영)**:
1. **가짜 IO는 경로별로 키를 나눈 저장소여야 한다.** 가짜 디스크를 단일 변수(blob) 하나로 두면, 수정 후 기기별 경로가 달라져도 가짜 IO가 경로를 무시해 **여전히 한쪽이 이긴 것처럼 보인다** → 거짓 실패("수정이 듣지 않았다"로 오독).
2. **인터리빙은 `setOriginalIme` 내부에서 강제해야 한다.** `setOriginalIme`은 자기 안에서 다시 읽으므로, 두 호출을 순차 `await`하는 하네스는 **재현에 실패한다**(거짓 음성 — 실제로 확인됨, `spec.md` §C.1 재현 하네스 관측). 읽기 배리어 등으로 메서드 **안쪽**을 겹치게 해야 한다.
3. **테스트는 경로가 아니라 IO를 주입해 작성한다.** 생성자 arg1의 의미가 M2에서 파일→디렉터리로 바뀌므로, 경로에 의존하면 M1 테스트 본문을 M2에서 수정해야 하고 전후 대조가 서로 다른 두 테스트의 비교로 변질된다.

- **전후 대조 의무**: 이 테스트는 **수정 전 코드에서 FAIL해야 한다**(한쪽 기록 소멸 = `plan.md` §F M1의 게이트). 수정 후 PASS로 전환된 것을 확인한다.
- 검증: unit(mock) + 전후 대조

### AC-IMESTATE-003 — 별개 프로세스 2개가 동시에 써도 양쪽이 살아남는다
- **Given** 빈 캐시 디렉터리와 서로 다른 시리얼 2개,
- **When** 별개 OS 프로세스 2개를 동시에 띄워 각각 자기 시리얼의 세션을 기록하면,
- **Then** 두 프로세스가 끝난 뒤 두 시리얼의 기록이 **모두** 조회된다.
- **판정 하네스**: 빌드 산출물 `dist/backend/ime-session-store.js`를 직접 임포트하는 스크립트 2개를 동시 실행한다(`node --input-type=module`). CLI `text` 명령을 거치지 않으므로 **실기기·adb가 불필요**하다.
- **정직성 조건**: 수정 전 동일 시나리오에서 유실이 관측되지 않았다면, 이 AC는 "유실 부재 확인"까지만 주장하고 "결함 해소 증명"은 주장하지 않는다. 자연 발생 타이밍 유실은 `spec.md` §C.1-⑰의 미관측 항목이므로, 어느 쪽인지 기록한다.
- 검증: e2e(호스트)

### AC-IMESTATE-004 — 특수문자를 포함한 시리얼도 충돌하지 않는다
- **Given** 손실 있는 변환에서 같은 값으로 붕괴하는 시리얼 쌍 `192.168.1.5:5555` 와 `192_168_1_5_5555`(붕괴는 `spec.md` §C.1-⑨에서 실행 확인),
- **When** 두 시리얼에 각각 다른 값으로 `setOriginalIme`을 수행하면,
- **Then** 두 기록이 서로를 덮지 않고 각각 조회된다.
- 이 AC가 실질 가드다 — `spec.md` §A.3-④가 기각한 재사용을 실수로 도입하면 여기서 실패한다. AC-008은 회귀 신호일 뿐이다.
- 검증: unit

### AC-IMESTATE-005 — 대소문자만 다른 시리얼이 분리된다 + 볼륨 특성을 스스로 관측한다
- **Given** 실제 파일시스템 위의 임시 디렉터리와 대소문자만 다른 시리얼 쌍 `ABC123` / `abc123`,
- **When** ① 먼저 볼륨 무구분성을 프로브한다 — **실제 캐시 디렉터리가 놓이는 볼륨에서** `probe` 파일을 만들고 `PROBE` 이름으로 접근 가능한지 확인 ② 두 시리얼에 각각 다른 값으로 `setOriginalIme`을 수행하면,
- **Then** 두 기록이 각각 조회된다.
- **프로브가 필요한 이유 (0.2.0 감사 반영)**: 인코딩이 소문자 hex이므로 두 시리얼은 애초에 다른 파일명이 되고(`414243313233` vs `616263313233`), 따라서 **대소문자 구분 볼륨에서도 이 테스트는 통과한다.** 프로브 없이 PASS로 기록하면 `spec.md` §C.1-⑲의 미관측이 관측으로 부당 승격된다. 볼륨이 무구분이 아니면 그 사실을 skip 이유로 기록하고 §C.1-⑲를 미관측으로 유지한다.
- **프로브 대상 볼륨을 명시한 이유 (0.4.0 — 3차 감사 N3-SF-5)**: 0.3.0은 프로브 위치를 정하지 않아 테스트가 쓰는 임시 디렉터리에서 프로브하는 것으로 읽혔다. 임시 디렉터리와 실제 저장소가 놓이는 `~/.cache`는 **다른 볼륨일 수 있고**, 그러면 §C.1-⑲를 해소하려던 프로브가 엉뚱한 볼륨의 특성을 기록한다 — 미관측을 관측으로 승격시키되 **틀린 대상을 관측**하는 셈이다. 프로브는 `resolveImeSessionStorePath()`가 가리키는 실제 캐시 디렉터리의 볼륨에서 수행하며, 임시 디렉터리와 볼륨이 다르면 **두 결과를 각각 기록**한다(테스트 본체는 임시 디렉터리에서 돌지만 §C.1-⑲가 묻는 것은 실사용 볼륨이다).
- 검증: unit(실FS)

### AC-IMESTATE-006 — 파일명에 예약 문자가 남지 않는다
- **Given** 경로 구분자와 콜론을 포함한 시리얼,
- **When** 파일명 인코딩을 적용하면,
- **Then** 결과 파일명에 `/` · `\` · `:` 가 없고, 결합된 경로가 캐시 디렉터리 하위를 벗어나지 않는다.
- 검증: unit

### AC-IMESTATE-007 — 레코드 내용으로 어느 기기인지 알 수 있다
- **Given** 임의의 시리얼,
- **When** 그 시리얼의 세션을 기록한 뒤 레코드 파일 내용을 읽으면,
- **Then** 내용에 **원본 시리얼**이 필드로 포함되어 있다.
- 근거: 파일명이 hex라 사람이 읽을 수 없으므로 추적성을 내용으로 보상한다(REQ-002). 조회 키는 파일명이며 이 필드는 조회에 쓰이지 않는다.
- 검증: unit

### AC-IMESTATE-008 — 손실 있는 정리 코드를 재사용하지 않았다 (양성 대조 필수)
- **Given** 구현 완료 상태,
- **When** 아래 **두 명령을 순서대로** 실행하면,
- **Then** ①은 매치가 **있고**(양성 대조 — 패턴이 유효함을 증명), ②는 매치가 **없다**.
```bash
# ① 양성 대조 — 패턴이 실제로 동작함을 먼저 증명한다
grep -nF 'replace(/[^A-Za-z0-9_-]/g' src/backend/adb-backend.ts
# 기대: :57 매치 (exit 0)

# ② 본 검사
grep -nF 'replace(/[^A-Za-z0-9_-]/g' src/backend/ime-session-store.ts
```

### AC-IMESTATE-018 — 호출자 파일이 수정되지 않았다 (기준 SHA 대비 + 양성 대조)
- **Given** M1 착수 직전에 기록한 기준 SHA(**`progress.md` §E.2에 남긴다** — 위치 근거는 아래),

```bash
# ① 양성 대조 — 이 SPEC이 반드시 수정하는 파일이 감지되는지 먼저 확인한다
git diff --name-only "$BASE" -- src/backend/ime-session-store.ts
# 기대: src/backend/ime-session-store.ts 출력 (감지됨)

# ② 본 검사 A — 내용 차이 (커밋된 변경 + 미커밋 작업트리 변경을 모두 잡는다)
git diff --name-only "$BASE" -- \
  src/backend/adb-backend.ts src/cli/commands/reset.ts src/cli/commands/doctor.ts
# 기대: 출력 없음

# ③ 본 검사 B — 커밋 이력 (내용이 원상 복구된 변경까지 잡는다)
git log --oneline "$BASE"..HEAD -- \
  src/backend/adb-backend.ts src/cli/commands/reset.ts src/cli/commands/doctor.ts
# 기대: 출력 없음
```
- **기준 SHA를 `progress.md` §E.2에 두는 이유 (0.4.0 — 3차 감사 N3-MF-4)**: 0.3.0은 `plan.md` §C에 남기라고 지시했으나, 그 SHA를 기록하는 주체는 M1 착수 시점의 `manager-develop`이고 **`manager-develop`은 `plan.md` 본문 수정이 금지**돼 있다(`spec-frontmatter-schema.md` § Forbidden ownership crossings). 즉 REQ-006의 유일한 기계적 증거가 **적을 곳이 없어서 실행 불가능**했다. `progress.md` §E.2(Run-phase Evidence)는 `manager-develop`이 소유하는 섹션이므로 거기 두면 합법적으로 기록된다.
- **단일 리비전 형태(`"$BASE" --`)를 쓰는 이유 (0.4.0 — 3차 감사 N3-SF-1)**: 0.3.0의 두 점 형태(`"$BASE"..HEAD`)는 **커밋된 변경만** 비교하므로 **미커밋 작업트리 변경을 놓친다**(감사관 실측: 미커밋 변경 → 미검출, 단일 리비전 형태 → 검출). 단일 리비전 형태는 기준 SHA와 **작업트리**를 비교하므로 커밋 여부와 무관하게 잡는다.
- **③이 별도로 필요한 이유**: 내용 비교만으로는 "수정했다가 원래 내용으로 되돌린" 변경을 잡을 수 없다 — 최종 내용이 같으면 어떤 형태의 diff도 비어 있다(감사관 실측: 원상 복구 → 두 형태 모두 미검출). PRESERVE 규율은 "결과가 같다"가 아니라 "**건드리지 않았다**"이므로 커밋 이력으로 판정한다.
- **양성 대조가 필요한 이유**: 이 AC는 "출력 없음"을 기대하는 **없음-검사**이므로 이 문서 서두의 **원칙 ②**가 그대로 적용된다. `$BASE`가 잘못 설정되거나 경로 인자를 잘못 쓰면 명령이 무조건 빈 출력을 내고 결함이 있어도 PASS한다 — 1차 감사가 이 AC에서 잡은 것이 정확히 그 형태였다. ①이 그 함정을 막는다. **0.3.0은 명령 형태만 고치고 양성 대조를 붙이지 않아 원칙 ②를 부분적으로만 지켰다** — 이 SPEC이 스스로 신설한 원칙을 자신의 AC에 완전히 적용하지 못한 세 번째 사례다.
- 검증 방식 라벨은 `greppable`이 아니라 `git(범위 비교)`다(grep이 아니다).
- 검증: git(범위 비교)

### AC-IMESTATE-022 — 배타 생성 실패가 오류로 새어 나가지 않는다 (0.2.0 신설)

- **When** `setOriginalIme("SERIAL-X", ...)`를 호출하면,
- **Then** 예외가 전파되지 않고, 기존 값이 유지되며, 호출은 정상 종료한다.
- 근거: **`EEXIST`** 실패는 오류가 아니라 "다른 프로세스가 이겼다"는 정상 결과다(REQ-007). 이것이 오류로 새면 `text` 명령 전체가 실패한다.
- **범위 한정 (0.3.0)**: 이 AC는 `EEXIST` 경로만 검증한다. 비-`EEXIST` 실패(`ENOENT` · `EACCES` · `ENOSPC`)가 삼켜지지 않는지는 **AC-027**이 담당한다 — 둘을 한 AC에 묶으면 "모든 실패를 삼키는" 구현이 이 AC로 PASS한다.
- 검증: unit

### AC-IMESTATE-023 — 툼스톤이 구 파일 폴백을 억제한다 (0.2.0 신설 — 좀비 차단)
- **Given** 구 단일 파일에 `SERIAL-A`의 기록이 **남아 있고**, 동시에 `SERIAL-A`의 툼스톤 `<enc>.cleared`가 존재하며 레코드 파일은 없는 상태(= `clear`된 시리얼의 기록이 구 파일에 남아 있는 상황),
- **When** `getOriginalIme("SERIAL-A")`를 호출하면,
- **Then** `undefined`를 반환한다 — 구 파일의 기록이 되살아나지 않는다.
- 이 AC가 닫는 것: 0.1.0 §C.2가 "허용된 한계"로 두었던 **구 파일 좀비**. 0.1.0은 이를 닫으려면 잠금이 필요하다고 주장했으나 그것은 미검증이었고, 툼스톤은 쓰기 주체가 해당 시리얼 하나뿐이므로 잠금 없이 닫는다(REQ-008).
- **0.4.0에서 이 AC의 무게가 커졌다**: 이관을 제외해 구 파일이 영구히 남으므로, 이 Given은 이관이 끝나면 해소되는 한시적 상태가 아니라 **영구 조건**이다. 툼스톤 억제가 실패하면 무효화된 기록이 매 조회마다 되살아난다.
- 검증: unit

### AC-IMESTATE-024 — 새 세션 시작 시 툼스톤이 멱등하게 제거되고, 그 사이 조회가 폴백으로 떨어지지 않는다 (0.2.0 신설 · 0.4.0 순서 검증 추가)
- **Given** `SERIAL-A`의 툼스톤만 존재하고 **구 단일 파일에는 `SERIAL-A`의 낡은 기록이 남아 있는** 상태(직전 세션이 종료됨),
- **When** `setOriginalIme("SERIAL-A", "ime.new")`를 호출하면,
- **Then** 세 가지가 **모두** 성립한다: ① 레코드 파일이 생성된다 ② 이후 `getOriginalIme("SERIAL-A")`가 `"ime.new"`를 반환한다(툼스톤이 억제하지 않는다) ③ **두 연산 사이에 끼워 넣은 조회가 구 파일의 낡은 값을 반환하지 않는다.**
- **③을 추가한 이유 (0.4.0 — 3차 감사 N3-MF-1)**: `spec.md` §A.3-⑧이 순서를 **레코드 생성 → 툼스톤 제거**로 확정했는데, 0.3.0의 이 AC는 **최종 상태만** 검증해서 반대 순서(툼스톤 제거 → 레코드 생성) 구현도 통과시켰다. 반대 순서의 중간 창에서는 레코드도 툼스톤도 없어 조회가 3단계 구 파일 폴백으로 떨어지고, 구 파일에 낡은 기록이 있으면 무효화된 값이 반환된다 — `reset`이 그 낡은 IME로 "복원"한다. **AC-015가 `clear` 쪽에서 같은 방식(중간 조회 삽입)으로 순서를 판정하는 것과 대칭이다.**
- **관측 방법**: 주입 IO로 레코드 생성과 툼스톤 제거 사이에 조회를 끼워 넣는다. 순서가 맞으면 그 조회는 1단계(레코드)에서 걸려 `"ime.new"`를 반환하고, 반대 순서면 3단계로 떨어져 구 파일의 낡은 값을 반환하며 실패한다.
- **Given에 구 파일 기록을 추가한 이유**: 구 파일에 그 시리얼 기록이 없으면 반대 순서 구현도 중간 조회가 `undefined`를 반환해 **차이가 관측되지 않는다** — 0.3.0의 Given으로는 순서를 구별할 수 없었다. 이것이 "상태만 보는 AC는 그 상태를 만드는 전이를 검증하지 못한다"는 2차 감사 교훈이 **세 번째로** 적용된 자리다.
- 툼스톤이 남아 있든 제거되든 조회 규칙 1단계(레코드 파일 우선)가 이긴다 — ①②가 그 우선순위의 성립을 판정한다.
- 검증: unit(mock) — 주입 IO로 두 연산 사이에 개입해야 하므로 mock이 필요하다(0.3.0의 `unit`에서 변경).

### AC-IMESTATE-025 — 구 파일 기록만 있는 시리얼의 `clear`가 툼스톤을 만든다 (0.3.0 신설 — 전이 검증)
- **Given** 구 단일 파일에 `SERIAL-A`의 기록이 있고, `SERIAL-A`의 **레코드 파일도 툼스톤도 없는** 상태(= 기록이 구 파일에만 있는 상태),
- **When** `clearOriginalIme("SERIAL-A")`를 호출한 뒤 `getOriginalIme("SERIAL-A")`를 호출하면,
- **Then** 두 가지가 **모두** 성립한다: ① 툼스톤 `<enc>.cleared`가 **존재한다** ② 조회가 `undefined`를 반환한다(구 파일 기록이 되살아나지 않는다).
- **이 AC가 막는 것 (2차 감사 N-MF-1)**: 0.2.0의 REQ-005가 "레코드가 애초에 없었다면 조회 결과를 바꾸지 않는다"를 무조건형으로 써서, **레코드 없으면 `clear`가 아무것도 하지 않는** 구현을 허용했다. 그러면 구 파일에 기록이 남은 시리얼에서 툼스톤이 생성되지 않아 REQ-008이 닫았다고 선언한 좀비가 그대로 열린다. 0.4.0에서 구 파일이 영구히 남으므로 이 경로는 **영구 조건**이 됐다. 그런데 0.2.0의 AC 어느 것도 이를 잡지 못했다 — AC-023은 툼스톤을 **Given으로 미리 만들어 두고** 조회만 검증하므로 손으로 만든 툼스톤으로 PASS하고, AC-016은 Given을 "구 파일도 없음"으로 한정해 이 경우를 건드리지 않으며, AC-015의 Given은 레코드가 존재하는 다른 경로다.
- AC-023(상태 검증)과 **역할이 다르다**: AC-023은 "툼스톤이 있으면 억제되는가", 이 AC는 "그 툼스톤이 실제로 만들어지는가".
- 검증: unit(실FS) — 툼스톤 파일의 존재를 확인하므로 실제 파일시스템이 필요하다.

### ~~AC-IMESTATE-026~~ — 폐기 (0.4.0)

**폐기 사유**: 검증 대상인 이관이 REQ-003 개정으로 제외됐다. 이 AC가 막으려던 결함(이관이 툼스톤 있는 시리얼의 레코드를 만들어 억제를 무력화)은 **원인 제거로 소멸**했다 — 0.4.0에서 레코드를 만드는 경로는 `setOriginalIme`(새 세션 시작) **하나뿐**이고, 새 세션이 무효화 상태를 대체하는 것은 의도된 동작이므로 게이트가 필요하지 않다(`spec.md` REQ-008). 그 하나뿐인 경로의 **순서**는 AC-024 ③이 검증한다.

### AC-IMESTATE-027 — 비-`EEXIST` 실패가 거부로 전파된다 (0.3.0 신설 · 0.4.0 이진 판정화)
- **Given** 주입 IO를 두 가지로 구성한 상태 — ① `wx` 생성이 `EEXIST`로 실패하는 구성 ② `wx` 생성이 `ENOENT`(또는 `EACCES` · `ENOSPC`)로 실패하는 구성,
- **When** 각 구성에서 `setOriginalIme("SERIAL-X", "ime.X")`를 호출하면,
- **Then** 두 가지가 **모두** 성립한다: ① `EEXIST` 구성에서는 호출이 **거부되지 않고 정상 종료**한다(기존 값 보존) ② 비-`EEXIST` 구성에서는 호출이 **거부된다**(rejected promise로 종료하고 오류가 호출자에게 전파된다).
- **0.4.0에서 이진 판정으로 바꾼 이유 (3차 감사 N3-MF-3)**: 0.3.0의 Then은 "구별되어 처리된다 … 감춰지지 않는다"였고 **무엇을 관찰해야 통과인지 명시하지 않았다.** 테스터가 관찰 대상을 정할 수 없으므로 어떤 구현으로도 PASS 주장이 가능했고, 이것은 REQ-007의 비-`EEXIST` 분기를 지키는 **유일한** 증거였다 — 1차 감사가 AC-008·018에서 잡은 공허 검사와 같은 부류의 재발이다. 0.4.0은 REQ-007에 "**거부한다**"를 명시하고 이 AC를 그 이분(거부 / 정상반환)으로 판정한다.
- **두 구성을 한 AC에서 함께 검증하는 이유**: `EEXIST`만 보면 "모든 실패를 삼키는" 구현이 통과하고, 비-`EEXIST`만 보면 "모든 실패를 거부하는" 구현이 통과한다. 후자는 정상 경합(다른 프로세스가 이김)에서 `text` 명령 전체를 실패시키므로 그것도 결함이다. **이분을 판정하려면 양쪽이 필요하다.** AC-022는 `EEXIST` 경로의 부수 계약(기존 값 유지)을 별도로 담당한다.
- 툼스톤 생성 실패도 같은 규칙을 따른다(`spec.md` REQ-007). 다만 툼스톤 **제거**의 `ENOENT`는 "이미 없음"이므로 정상이다(멱등).
- 검증: unit(mock)

### AC-IMESTATE-028 — 구 파일은 읽기만 되고 변형되지 않는다 (0.4.0 신설)
- **Given** 구 단일 파일에 기록 2건(`SERIAL-A` · `SERIAL-B`)이 있고, 그 파일의 **내용과 mtime을 미리 기록해 둔** 상태,
- **When** 폴백을 유발하는 조회(`getOriginalIme("SERIAL-A")`) · 기록(`setOriginalIme("SERIAL-C", …)`) · 무효화(`clearOriginalIme("SERIAL-B")`)를 모두 수행한 뒤 구 파일을 다시 확인하면,
- **Then** 세 가지가 **모두** 성립한다: ① 구 파일이 **여전히 존재한다**(rename·삭제되지 않았다) ② **내용이 바이트 단위로 동일하다** ③ **mtime이 변하지 않았다**.
- **이 AC가 지키는 것**: 새 REQ-003("구 파일은 영구 읽기 전용")의 **유일한 기계적 증거**다. 이관·rename·폐기·항목별 삭제 중 어느 것이 구현되어도 ①②③ 중 하나는 반드시 깨진다.
- **폐기된 AC-013을 대체한다**: AC-013은 "이관을 마친 뒤 구 파일이 조회 대상에서 빠지는가"를 물었고 폐기 방법(rename·표식·삭제)이 무엇이든 통과해야 했으므로 절차를 느슨하게 열어 두어야 했다. 이 AC는 허용된 동작이 하나(아무것도 하지 않음)이므로 **판정이 이진**이다.
- **mtime을 함께 보는 이유**: 내용이 같아도 파일을 다시 쓴 구현(읽고 그대로 되쓰기)은 REQ-001이 금지한 공유 파일 read-modify-write를 재도입한다 — 내용 비교만으로는 그것을 잡지 못한다.
- **`SERIAL-B`를 `clear`하는 이유**: `clear`가 구 파일에서 항목을 지우려 시도하는 구현(0.2.0에서 REQ-001 위반으로 기각된 설계)을 이 AC가 잡는다. 무효화는 툼스톤으로만 표현되어야 하며 구 파일은 그대로 남는다.
- 검증: unit(실FS) — 파일 존재·mtime을 확인하므로 실제 파일시스템이 필요하다.
